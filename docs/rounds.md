# The rounds

The local model works in rounds on the bench, and every round is recorded (mqucifer/print-shop#17, M18 in mqucifer/project-print `ROADMAP.md`, ADR 0010 there). It closes the loop [the bench](bench.md) left open: intake, make or change, read the bench's answer, change again. Limits start high and are lowered from evidence, there's no budget on thinking, and every failure has a named ending.

```
scripts/rounds.py start NAME --request FILE [--reference FILE]... [--trim-reasoning] [--start-lessons-chars N]
scripts/rounds.py resume NAME [--note FILE] [--from WHO] [--reopen-needs]
scripts/rounds.py resume NAME --from sponsor|"stand-in: <who>" [--note FILE]   (at `questions`)
scripts/rounds.py resume NAME --approve --by WHO [--note FILE]
scripts/rounds.py resume NAME --send-back --by WHO --note FILE [--reopen-needs] [--fresh]
scripts/rounds.py resume NAME --close --by WHO --note FILE
scripts/rounds.py status NAME
scripts/rounds.py stop NAME
scripts/rounds.py summary NAME
scripts/rounds.py read-back NAME [--ledger FILE]
scripts/rounds.py after-action NAME
scripts/rounds.py lessons [RUN] [--ledger FILE]
scripts/rounds.py lessons accept|edit|reject|retire|promote ID --by WHO ...   (accept and edit take --part-kind K|general)
scripts/rounds.py lessons score RUN ID --score used|not_used|in_the_way --by WHO [--calls N,N] [--route R]
scripts/rounds.py lessons load FILE --by WHO
scripts/rounds.py lessons copy LEDGER ID --by WHO [--ledger FILE]
scripts/rounds.py refine NAME --nozzle MM --filament [COLOUR=]NAME...
scripts/rounds.py refined NAME
scripts/rounds.py proposal NAME ID --approve|--reject --by WHO [--note FILE]
scripts/rounds.py start NAME --request FILE [--reference FILE]... --right FILE
scripts/rounds.py scores NAME [--right FILE] [--ledger FILE] [--keep]
scripts/rounds.py replay NAME N [--times K] [--label L] [--out DIR] [--skill NAME=FILE | --reply CALL.K=FILE | --skills-card FILE | --lesson FILE | --replace OLD NEW | --tool NAME=FILE]
```

It needs the bench's image (`scripts/bench.py build`), and LiteLLM on :4000 with print-shop's key from `~/.config/print-shop/.env`. It uses `crew-code-think`, and probes nothing else. **A run's record says what reasoning effort its alias sends** (`runs.reasoning_effort`, and `reasoning_effort` in `summary.json`), read at `start` from LiteLLM's own `/model/info` for this key: the alias's `litellm_params.reasoning_effort`, or its `extra_body`'s, or in `extra_body.chat_template_kwargs`. It's no model call, and SGLang isn't reached. If LiteLLM won't say, the record says `unknown` and why (`reasoning_effort_from`). Nothing else is kept from the answer, which can name a server's address. The effort stays as it is (the Sponsor, 2026-11-03): it's recorded, not changed. **A run names its code,** so `start` and `resume` refuse a checkout with uncommitted changes. As in `cad_eval`, run from a checkout nothing edits until it ends: `git worktree add --detach ../run-<commit> <commit>`. One session runs under a root at a time (`.session.lock`). Runs live in `~/print-shop/design-runs/`, off this public repository, and `start` refuses a folder inside it.

## A run

**Intake.** From the request and any reference files, the model reads what it's given and asks what it needs, as an interview. `questions` writes them to a file, with any pictures the model made, or with none a sheet of the given STEP and STL files that the harness draws, and the process exits. A person relays them, writes the answers to the file it names, and runs `resume`. Before its needs, it writes down how the job is built with `breakdown` (below). `needs` ends intake. Each need says how it's checked, by a bench command and its limit, by the side a file lies on the bed (a bed need), or by the Sponsor's eye. A quote from the Sponsor is held to their words. Writing and running are open throughout. `needs` with `try: true` reads each bench check against the files as they stand, and settles nothing, so it needs no breakdown. Each reading reaches the ledger's `tries`. A need's `source` says where it came from: `request`, `answer`, `note` or `pick`, each with a quote held to that source's words, so what a person relayed in a note isn't marked `derived`.

**A need's fields are a schema** (mqucifer/print-shop#93). `needs` refused for a mistake is the largest refusal class: 106 refusals in 54 runs, and of their 407 lines 158 a `quote` left out (44 runs), 39 a field the need doesn't have (7 runs) and 37 a limit not in its quote (about 15 runs); 38 of the 106 were tries. The fields were only in the tool's words, `quote` in brackets, so the `needs` tool's items are now a JSON schema naming each field (`tools.need_item`): `quote` says it's required for `request`, `answer`, `note` and `pick`, and `check` lists its own fields, one level deep. The rules stay `needs.read`'s. **A `try` reads its checks even when a need's form is wrong:** it's refused as settling would be, naming each mistake, with each check that can be run read beside them, and kept in `tries`. Only a check whose command doesn't parse, names no bench command of the run's, or the bench's own parser can't read is left out. A settle is refused as before.

**The breakdown comes first** (mqucifer/print-shop#36). In all three stained-glass runs the model read the reference for what's in it, not how it's built: on `suncatcher-2` it drew each ring as one loop where short bars cut them, and the frame came apart into three bodies. So `needs` is refused until `breakdown` has named the parts, what holds or connects each to the rest, and what the look rests on. It's held to its shape, not its words: each part named once, each join naming parts that are there, and with more than one part, every part in a join, since a part nothing holds is the one that comes apart. It's general to any part: a bracket's plate, arm and brace, or a lamp's shade and socket ring. It's kept in `breakdowns/n.json`, `breakdown.md` and `work/record/breakdown.md`, and the ledger's `breakdowns`. The model can send it again whenever it finds it wrong, and the plan stop shows the latest.

**Rounds.** The model makes and changes the part, and calls `done` when it believes the needs are met. The harness then runs the script again and each need's check itself, so the model's word and a tool's success don't count:
- The clean run has a fresh container, over a plain copy of `work/` with no links, nothing a run left, and all geometry outside `references/` taken away.
- Each bench need then runs in another fresh container, where no model code has run. `params` runs the script by its nature, on a scratch copy, so its reading is as good as its own second check.
- `DISAGREE` and `NO ANSWER` never pass, whatever a need says.
- An eye need passes on a pick, and on nothing else. A stand-in's passes it too, so a run can be proved with no Sponsor there, and the reading says who it was.
- A bed need passes when `done`'s `on_bed` gives its file its side, and on nothing else (mqucifer/print-shop#73, below).
- **A pick holds only for what it saw.** Each file on its sheet is held by a hash of what it contains (`paths.content_hash`), and the clean run has to leave the same, with some of the `part` among them. Otherwise the need fails, saying which file changed, and it's asked again. A STEP file's header names the second it was written, so its hash starts at its `DATA` section, or every clean run would count as a change. A pick of `none` takes back any pick before it, and a pick from before this holds for nothing.
- **Or by its geometry, where only the bytes differ** (mqucifer/print-shop#180). On eval-organic-3 a clean run's `pieces build` wrote two pane files with another 17th digit in a line's point, so a stand-in's pick of the finished suncatcher didn't hold, round 5 began, and the model spent about 17 calls testing whether its own pipeline was deterministic. `pieces build` now writes the same bytes every time ([bench](bench.md)); this is the second guard, for anything else that writes the same part two ways. Where a picked file's hash isn't among what the clean run left, the clean run left a STEP or STL file of the same name, and the ask's kept copy (`asks/n/variants/PICK/`) is what was picked, the bench reads both in a container (`bench/solids.py`): each solid's volume, area, centre of mass and box, and each of its faces' kind, area and centre. Ordered by those figures, each must agree to arithmetic's noise (`limits.ARITHMETIC`, a millionth of a mm, or of a volume or an area). Then the pick holds, and the reading says it held by geometry and why. Any change to the geometry, a pane moved, a hole moved inside a body whose volume and box stay the same, a face more, breaks it as before, and the reading says what differs. On two builds of that map whose frame and pane file differed, every figure agreed to the last digit. It's read only at `done`: an `ask` still names an eye need open by the files' hashes.
- A `part` a clean run didn't leave isn't met, whatever the needs read.

Needs that fail go back in `done`'s reply, with each reading against its limit and the last round's, and the next round starts from what's there: the part, the script and `record/ROUNDS.md`. The conversation carries on, with its reasoning.

## The request's form

A request is free text, as it always was, with up to four headings of its own (`request.py`). Each line under them is one line of the request, `- ` or `1. ` before it or not, and a line that goes on indented is joined to the one above.

| Heading | Its lines | Held how |
|---|---|---|
| `## Requirements` | What the part must do, ids `R1`, `R2` | Each is covered by a need that names it in `covers`, or `needs` is refused naming the lines left over, with their words |
| `## Non-negotiables` | What mustn't change, ids `N1`, `N2` | Each is covered by a need marked `fixed`, whose quote is from that line. A need that covers one is fixed. Where the line holds a figure, the need says in `figure` how it's read, and where something changes it, which: a lip before or after play. The model is told to ask with `questions` where the request doesn't say. Its check carries the figure, at both ends where the line gives a range or an exact figure (below) |
| `## Kind` | One word, such as `stained-glass` | Read and kept, and `start` gives the lessons for that kind of part (`lessons.part_kind`) first, then the general ones, under its budget, and loads its toolset: its bench commands, measures and skill (below). A kind with no toolset of its own has the core |
| `## Stops` | What's shown before the run goes on, in order, ids `S1`, `S2` | Below. The line `no plan` leaves the plan out |

**A request's pictures and reference files go in at `start`** (`--reference`), with the request, so the plan is written from them.

**An object the part must fit goes in with the request as a reference,** such as bought hardware or a tealight (`start --reference`). Whoever writes the request draws it from its maker's figures; the model never makes it. A need reads only the part and `references/` (mqucifer/print-shop#45), and on `tealight-1` the fit was checked against a tealight the model drew.

**A request that gives a part to change says what else may change.** On `eval-tip-1` the model read a request for a pane as leaving the given frame as it was, and didn't ask.

Coverage is held by ids, as `needs` holds quotes, and nothing is guessed from words: the only reading of a line's words is whether it holds a digit. **A line is covered by an eye need only where no bench command measures it,** and the harness can't know that on its own, so an eye need that covers a line says why in `check.no_bench`, and the person reads it at the plan stop. Where mqucifer/print-shop#37 settles which command measures what, that list can hold it too.

**A request in the old free form still runs.** With no `## Requirements` or `## Non-negotiables`, it has no lines, and nothing is checked for coverage. It still has the plan as its stop, and the breakdown before its needs. A run started before this has no form in its `state.json`, and carries on as it began: no lines, no stops, no breakdown asked for.

The first message lists every line and stop by its id, and the ledger's `request_lines` keeps them. The `needs` table is inserted into by position by older code, so each need's `covers`, `fixed`, `figure` and `no_bench` are a row of `need_marks` instead.

A worked example, of a part that isn't stained glass:

```
A wall bracket for a small shelf, in PETG. It should look plain and sturdy.

## Requirements
- It holds a 6 kg shelf without bending.
- Two screw holes, 4.5 mm across, for the wall.
- It should look plain, with no sharp corners.

## Non-negotiables
- The arm is 120 mm long, from the wall to its tip.
- The plate is at least 4 mm thick, measured
  after the countersinks are cut.

## Kind
bracket

## Stops
- the 2D profile of the arm
- one bracket printed as a test, before the pair
```

Its needs cover `R1` to `R3`, `R3` by eye with its `no_bench`. `N1`'s need is `fixed`, quotes "The arm is 120 mm long", and says in `figure` that the length is from the wall face to the tip. `N2`'s is `fixed` too, and its `figure` says the thinnest is read after the countersinks, as the line says. The stops are `plan`, then `S1` and `S2`. `tests/test_intake.py` runs this request, and a lamp's.

### A fixed need

**Its check counts only at its own settings** (mqucifer/print-shop#37, criterion 2). `suncatcher-2` passed `capture` at `--min-lip 0.25` where the request said 1.2. A `bench` call of a fixed need's check with any other argument is answered first, after its exit and before the bench's own verdict, as `NOT THE REQUIREMENT`, with the need's words and its own command, from the first try, pass or fail. Its reading can't pass the need, as `done` runs the need's own command, and a pass at other settings doesn't start the nudge's count again. Its call's `detail` has `not_the_requirement`. A need that isn't fixed says the same, more quietly, after the bench's answer, as before.

**Its check carries its line's figure** (mqucifer/print-shop#52). On `eval-thick-2` the line was a range of 1.5 to 1.8 mm and the need `thickness ... --max 1.8`, with no `--min`; on `eval-choice-1` a rim of at least 1.2 mm was checked by an opening's area. Both were said at the plan and settled. Now `needs` refuses a fixed need whose check doesn't carry each figure of its line (`figures.py`), naming the figure, the end and what the checks do carry:
- **A figure** is a number with its unit (`mm`, `cm`, `%`, degrees, `mm²`, `mm³`). A bare number is a count, which no limit carries, and is still only said at the plan.
- **Its ends come from the line's words, and only these.** `A to B`, `A–B` or `between A and B` is a range, A its low end and B its high. "At least", "no less than", "minimum" or "more than" before a figure, or "or more" after it, is its low end alone; "at most", "no more than", "maximum", "up to" or "less than", or "or less" after it, its high end alone. Any other figure is exact, and both ends.
- **What carries an end,** across the fixed bench needs that cover the line: a `number`'s `at_least` (low) and `at_most` (high), an option `--min` or `--min-...` (low), `--max` or `--max-...` (high), and any other option, a setting the check reads the part at (`--full-rim 1.2`), which carries both. Each at the request's own figure. An exact figure one option carries where its command has no option for the other end (`capture --min-visible`) is carried as far as a check can: `reports.BOTH_ENDS` lists the options that pair, read from the bench's parser by `tests/test_reports.py`.
- **A check by another measure doesn't carry it:** an area for a rim is refused, as the figure isn't in it.
- **A figure the Sponsor changed by a note** is the note's: the fixed need quotes the note, and carries its figures. A line only an eye need covers isn't held to this; that need says in `no_bench` why no bench command measures it.

Replayed on every needs version the evals settled, it refuses `eval-thick-2`'s first and `eval-choice-1`'s first, and nothing else (`~/print-shop/proofs/m18-needs/replay_needs.json`).

**It changes only by the Sponsor,** through `resume --reopen-needs` with a note, `--from sponsor` or `--from "stand-in: <who>"`, or a send-back with `--reopen-needs`, which has both. Any other reopening, such as a note from the people running this, opens the other needs and says the fixed ones stay. A `needs` that drops a fixed need, unmarks it, or changes its check, its quote, its lines or its `figure` is then refused, naming its check as it was. The opening holds for one settling.

**Whoever reopens is told** (mqucifer/print-shop#66). On `eval-lid-1` and `eval-fit-2` `resume --reopen-needs` with no `--note` kept the fixed needs locked, only the model was told, and each lost a round. Now the resume prints, before the model goes on, whether the fixed needs opened, by whose note, or that they stay locked and why, with what would open them. A pick's `fix_first` is written by someone who decides, so on a resume from that pick it opens them as a note does: "as the pick's fix-first says". Of the 24 reopenings the evals and runs recorded, 3 left the fixed needs locked (`eval-fit-1`, `eval-fit-2`, `eval-lid-1`), and each resumed from a stand-in's pick with a fix-first, which now opens them (`~/print-shop/proofs/m18-refine/batch5/reopens_replay.json`).

**It holds its figures, not its file list** (mqucifer/print-shop#59). On `suncatcher-3` the rim needs were settled at the plan as `capture ... --panes 14`, with `light` and `thickness` over `pane_1.step` to `pane_14.step`. After the Sponsor's two rings and the tessellated centre the part had 27 panes with new names: every figure still held, but four needs failed on the count and the names alone, and the operator reopened them by hand. So a settled need's frame, panes, the frame's other parts (`--with`) and pane count follow the part, as the latest `glass` declares it, at `done`, at each ask, in the held checks and in `NOT THE REQUIREMENT`. Its figures stay as settled, and changing one still takes `--reopen-needs` with the Sponsor's note.
- **Which arguments.** `reports.ROLES` names them by the bench parser's own names, read back by `tests/test_reports.py`: `light`'s frame, panes and `--with`, `capture`'s frame and `--panes`, `thickness`'s panes, and `panes`'s and `pause`'s frame. A frame the part renamed follows where the part has one frame. A need on a given reference `glass` doesn't name, the "before" state, stays as it is.
- **The pane count is the bodies in the pane files, not the files** (mqucifer/print-shop#153). One file may hold every pane of a colour, as `pieces build` writes them: on the first traced scene six colour files held 52 panes, the harness's own `capture` ran at `--panes 6` and failed, and a need settled at `--panes 52` was rewritten to 6. When `glass` is declared the harness counts each pane file's bodies itself, a STEP file's solids by the entities it lists and an STL's by where its faces join (`standing.bodies_in`), and keeps the count with the declaration (`pane_bodies` in `state.json`): the standing `capture` and a settled need's `--panes` are that count. Where a file can't be counted, a file is a pane, as before. Two files holding five panes read five, and one file of one pane reads one.
- **What's kept.** `state.json` and `needs/n.json` keep the needs as settled. `done` writes what it ran in `rounds/n/followed.json`, says each need that followed in its reply, and an ask says them in `question.md` under "Needs that follow the part". A fixed need sent again over the part's own files in their roles is the same check, so it's kept.
- Replayed on `suncatcher-3`'s plan needs with its last `glass`, it moves exactly the four needs the operator reopened, each to the command the hand reopening gave, byte for byte (`~/print-shop/proofs/m18-stops/follow_suncatcher3.json`).

**A figure that's its command's own input checks nothing** (mqucifer/print-shop#59). On `eval-fit-1` the fixed fit need was `panes ... --clearance 0.25` with `gap_3d_mm` between 0.24 and 0.26, and passed: `panes` cuts its own pane 0.25 mm in from each opening, so its gap is 0.25 whatever the part's pane is. `reports.INPUTS` lists the options a command builds what it measures from, with the numbers that read them back, and `tests/test_reports.py` reads the build from the bench's code. Settling refuses a need whose `number` reads one back, a line's figure given as one, fixed or not, and a fixed need's figure carried only by one, which carries none. Each names the command that reads the part's own file: for a pane's fit, `clearance PANE.step FRAME.step` with `pairs.0.gap_occt_mm`. Replayed on every needs version the evals and runs settled, it refuses 11 of 54, each a fit need on `panes` at the line's own play (`eval-fit-1`, `eval-tip-1` to `-3`, `eval-through-2`, `eval-unnamed-1` and `-2`), and nothing else (`~/print-shop/proofs/m18-stops/echo_replay.json`).

**With or without a number** (mqucifer/print-shop#66). On `eval-fit-2` the fixed play need was exit-only, `capture frame.step ... --clearance 0.25`, its `figure` naming `capture`'s `--clearance` as what carries the play: `capture` cuts its own pane `--clearance` in from the pocket too, so 0.25 came back by construction and the given pane was never read. So `capture`'s `--clearance` is in `reports.INPUTS`, with no number that reads it back, and a figure carried only by a build input is refused, fixed or not, number or none, naming the command that reads the part's file. Where another need on the line reads the figure off the part, or the same need reads another of the line's figures, the input is the setting those are read at, and stands: a rim sized before a given play is read at that play by `capture --full-rim R --clearance P`, the line's own check. A `number` that reads an input back carries nothing either. Replayed on every needs version the evals and runs settled (66), it refuses mqucifer/print-shop#59's 12 as they were, `eval-fit-2`'s first, and nothing else (`~/print-shop/proofs/m18-refine/batch5/needs_replay_branch.json`, against `needs_replay_main.json` on main's code).

**A number's path is walked when its need is settled** (mqucifer/print-shop#66). On `eval-sleeve-1` an `info` need was settled on `bounds_mm.1.z` and `bounds_mm.1.x` before the file existed: `bounds_mm` is two corners of three, so neither path is there, and the run ended `blocked` with the part right. `reports.SHAPES` holds what's under each number that's the same whatever the part: a number, text, true or false, a list of a fixed length (a point's x, y and z), rows as many as the part makes, or a row's fields. `needs` walks each `number` through them with no file to run on, and refuses one that names a place by letter, goes past a list's end or under a number, names a field a closed row never has, or ends on a list, a row, text or a flag, saying how to name it (`bounds_mm.1.z` is `bounds_mm.1.2`). What depends on the part, such as a field a row may or may not have, is let through. A `try` says the same beside its readings. `tests/test_bench.py` holds every command's answer on its fixtures to the shapes. mqucifer/print-shop#65's numbers are walked the same: `clearance`'s `pairs.N.gap_mm` (the verdict's gap) and `lift.mm`, and `edges`' `groups.NAME.least_radius_mm` for `upright`, `top`, `bottom` or `side`, and `selected.NAME.least_radius_mm` for a `NAME` the need's own `--box` or `--facing` gives; a group that isn't one, a field a row never has, or a selection the command doesn't name is refused, naming what is. In the same replay it refuses `eval-rings-1`'s first, as before, and `eval-sleeve-1`'s first, and nothing else.

## Stops

**A stop the request names is held** (mqucifer/print-shop#38). On `stainedglass-1` the plan was written at call 5 and nobody saw it, on `cup-1` the test of one pane was skipped, and on `suncatcher-2` the 2D layout's `ask` was skipped, and its fault cost a redesign. Each of `## Stops` is shown with `ask`, naming it in `stop`, in order. Until its ask has a pick, `done` and the next stop's ask are refused, and the refusal names the stop that's open. **A stop holds what's handed over, never the work:** writing, running, the bench and any other `ask` stay open throughout, and an ask that isn't the open stop says that it's still open.

**The plan is the first stop,** `plan`, unless `## Stops` says `no plan`. It's asked once the breakdown and the needs are settled, as it shows both: the model's `plan`, in its words, the breakdown, each need with the lines it covers, whether it's fixed and how its figure is read, each line with the needs that cover it, and any figure of a non-negotiable that no fixed need's check carries: a bare number, or a line only an eye need covers, since a figure with its unit is refused at `needs` (mqucifer/print-shop#52). The plan comes after the needs so the person sees what the work will be checked against, the fixed needs above all: a figure read the wrong way is caught there, before the first round, and `resume --reopen-needs` with the pick reopens them.

**A pick passes the stop. `none` leaves it open:** what was shown wasn't right, so it's shown again before anything's handed over. The model's told which, and the next stop. **A `none` at the plan reopens the needs too** (mqucifer/print-shop#45), since the plan shows them: on `eval-tip-1` the stand-in's reason named the fit need's check, the model was refused (`needs_settled`) when it moved the need onto the frame, and the operator reopened them by hand. The model's told with the pick, and the fixed needs stay as they are: they change only through `--reopen-needs` with the Sponsor's note. At any later stop a `none` opens nothing. `state.json` has each stop passed, with its ask, the pick, who made it and at which call. The ledger's `picks.stop` names the stop an ask showed, and the view `stops` gives each stop asked, what it is, at which call, and picked when and by whom.

**A question with options takes them as picks** (mqucifer/print-shop#66). On `eval-change-2` ask 4 asked which of two outlines, A or B, both drawn in one picture, and the pick of A was refused: a picture's picks were yes or none. `ask` takes `options`, the choices drawn in its pictures, each `{"name": "A", "about": ...}`, and each is a pick, said in `question.md` and the waiting line. Options of the part's own files are `variants`, as before, and the two don't mix. A question that offers lettered options, "A or B", with neither is refused (`options_unnamed`), saying how. Of the 85 asks the evals and runs sent, it refuses only that one (`~/print-shop/proofs/m18-refine/batch5/asks_replay.json`).

**Eye needs on one sheet go in one ask, and nothing is asked twice** (mqucifer/print-shop#59). On `suncatcher-3` the layout stop was raised again at 08:54Z on the picked picture, byte for byte, only to say the fix was understood; at 12:11Z and 12:16Z two eye needs were confirmed one stop each on the same layout, and the third set went in one only after the stand-in asked. Three of its nine stops asked nothing new.
- **`need` names every eye need a sheet answers,** as a list, and one pick answers each. An ask that names some has each other open eye need in `need` too, or in `later` with why it needs another sheet, which `question.md` shows; otherwise it's refused (`eyes_apart`). An eye need is open until a pick holds for the files as they stand.
- **An eye need is asked on the part's own files,** as `variants`: its pick holds only for what it saw, and `done` holds it to the part, so a pick on a picture the model drew could never pass it. Such an ask is refused (`eye_on_picture`), with pictures welcome beside the variants.
- **A stop, or eye needs, asked again on what a pick answered** (not `none`), with every variant's files and every picture unchanged by hash, and the plan's text at the plan stop, is refused: "Already picked; go on", naming the ask, who picked what, their reason and any fix-first (`already_picked`). A changed file or picture is something new.

Nothing is refused, and `ask` stays open. **The side is the one the part prints on** (`downward.laid_on`, mqucifer/print-shop#192; the Sponsor, 2026-11-20: printability reads the side a part prints on): `done`'s `on_bed`; then a bed need's; then, for a part of an assembly file (`docs/bench.md`'s `load`), a side square to its `layers`, the one the latest `fit-bed` laid its file on, or `-` that axis where no `fit-bed` has said; and `-z` only where nothing says. The assembly is the one the run's latest `fit-bed` or `load` read, or any JSON file in `work/` whose parts give `layers` (`print_sides.py`). Every reading says which side it used and why, in its words ("lying on its -x side, as its layers run along x in `assembly.json`, and `fit-bed` laid it on -x at call 12") and as `side_from` beside `side`; an `on_bed` side across an assembly's `layers` says that too. *Evidence: a leg piece the assembly said prints on its side, `layers: x`, laid on -x by `fit-bed`, was read lying on -z: flagged for faces that are walls on its side, and its real overhang, a tail inset 3.2 to 5 mm on every side hanging over air along 12 mm, missed (lesson runs19-joint:10). Made up: a bar 30 x 30 x 100 mm with that tail on top and a slot through it along x reads 232.5 mm² under the tail lying on -x and nothing at the slot, and lying on -z 276.5 mm² at the slot's roof and nothing under the tail (`~/print-shop/proofs/m20-lock-side/leg_piece.json`).* *Evidence: on `eval-neon-strip-2` the request said the channel prints with no supports, the run built its catch with a flat 0.6 mm underside, and nothing in the needs or the stops read it (lesson runs13-neon:16); a design run's lid had a flat 1.5 mm ledge the Sponsor caught by eye.* Made up: a tray with a ledge 3 mm in from its walls reads 342 mm² of its 396 mm² ceiling at z 16 and doesn't pass; the same with a 45 degree underside reads none.
- **A paused frame is read with its panes in place** (`downward.py`, mqucifer/print-shop#153). A stained-glass frame's top lips print over its panes, after the pause, and read alone each was a ceiling over its pocket: on the first traced scene, 4,761 mm² at the pocket's ceiling. So a frame that `glass` declares, lying flat on its -z or +z side, is read with its panes under it, each turned as the frame is, as `pause` already has them: `features.overhang_to_support` takes what else stands beneath, and a face with a pane right under it is carried. None of a pane's own faces is read there, and each pane file is still read alone. The reading says how many panes were in place and what it reads without them (`panes_in_place`, `without_panes_mm2`). A frame with one pocket 20 mm square and a 2 mm lip reads 112.6 mm² alone, the lip less the 0.4 mm beside the pocket's wall, and none with its pane; a ledge elsewhere on that frame still reads (`tests/test_paused_frame.py`), and so does a built frame of ten panes on the bench's own meshes (`test_a_built_frames_lips_pass...`).
- **Files printed together can't take the same space.** `done` names `groups`, the ways the part prints, each with its own files, and a file of `part` in no group prints with every group, as panes do. With no `groups`, the whole `part` is one. A pair in one group that shares more than 0.5 mm³, by Manifold and again by OCCT's `common`, isn't met. `clearance` across 16 files ran past 600 s, so this is a helper that asks only that (`bench/overlap.py`).

Each of these is in the ledger's `standing` table, by file and its hash, and a round where every need passed and these didn't has `met` 0.

`done` also asks what kind of change the round was (`fix_shape`) and for the model's closing words (`closing`), so neither column is empty. Both are in its own words, kept as such, and decide nothing.

**What's the part.** `done` names the files that are the part (`part: ["stand.step"]`). A need's check reads files of the part or the given references, and nothing else (mqucifer/print-shop#45): a test piece a need reads is given, under `references/`. Each entry is one row of the sheet, and files seen together are one entry: `{"name": "wide", "files": ["base.step", "lid.step"]}`. `final-sheet.png` draws those alone, so two outlines in one `part` aren't drawn on top of each other. It's the model's word and it decides nothing else. A sheet's `files` are what the Sponsor takes for the part too, and `test_pieces` on `ask` shows others, see-through in grey and marked.

**Approval is a stop.** The Sponsor's definition of done (2026-11-02): design rounds, their approval, a refinement pass whose findings go in the ledger, then the learn loop. `met` means every need passed its check, and every file the harness's own, and doesn't mean approved. When they do, the run stops instead of ending, and `done` can't end it. `approvals/n/` has the sheet of the final part, drawn in the `looks` `done` gave, and `stop.md`, with each reading, `thin` on each file, any need swapped since the last stop, and the model's closing words, and `what_next` prints those words too. The model is shown the same sheet.

**The delivered result is `review/`,** written by the harness at each stop for approval from its records, into `approvals/n/review/` and copied to the run's `review/`. One folder a group, lettered (`A-two-parts`, `B-one-frame-with-pause`), holds its own files under their names and every shared file, each named by its number, its label and its colour from `looks` (`pane_01-cup-blue.step`). Its README gives the size, which files take the same space and so are never loaded together, a table of the shared files, each requirement's reading against its limit and the files its check read, `thin` on each file, and what wasn't checked: files no need's check named, eye needs that passed on a pick, `thin`'s unsure answers and the swaps. The model's closing words are under their own heading. Nothing in it is sliced or printed.
- `resume --approve --by WHO` ends the run as `approved`, with no model call, and then the model writes its after-action review (below). The run is approved whatever the review does.
- `resume --send-back --by WHO --note FILE` goes on as a new round, with the note. A plain `resume` is refused here. With `--fresh`, the conversation starts again from the record, the note its first message after the start, as the end checks' send-back does (mqucifer/print-shop#150). It's opt-in until reruns show whether it helps.
- `resume --close --by WHO --note FILE` ends a run without approving it, below.
- Anyone else is `--by "stand-in: <who>"`, as at a pick. `decisions` holds which, and who.
- A send-back after approval is by hand, with the same `--send-back`. **It withdraws that approval** (mqucifer/print-shop#150; the Sponsor, 2026-11-15: "I don't want a success in a ledger when new information contradicts it"). The approval's own row in `decisions` gains `withdrawn_at`, `withdrawn_by`, `withdrawn_why` (the send-back's note) and `withdrawn_decision` (the send-back's row), so "approved, then withdrawn" is `decision = 'approved'` with `withdrawn_at` set, and an approval that stands has it empty. `state.json`'s `withdrawn` and `summary.json`'s `approvals_withdrawn` list each one, and `read-back` writes it to a ledger whose row doesn't say so yet. It becomes automatic only once there are more mechanical checks or agreements ahead of time. The refinement pass is still to come; the delivered result is `review/`, below.

**Stopping for the Sponsor.** Only `ask`, where form is at stake, at a stop, or when the model is stuck, in two calls. It works at any stage, with one variant of the files as they stand, and the answer comes back as a pick and its reason, with any `fix_first` and `--note`. **It needs no part file:** `pictures` shows PNG or JPEG files the model made, such as a 2D layout drawn with matplotlib, as they are, and at the plan stop `plan` is its text. A picture is shown to the model first, by the same reading as `read`, and goes in `asks/n/pictures/`, held by its hash as a variant's files are. On `cup-1` the model read its own matplotlib drawing right, and the bench's render wrong, so a plan goes as the model drew it, with no render in between and no container needed for geometry that isn't there yet. With no variants, the pick is `yes` or `none`. `ask` names the variants and `render` draws the sheet, which goes to the model and not yet to the Sponsor. It can add close-ups (`close`), cut-throughs (`cuts`: `z=3`, or `x=50,y=20:40` for a pane in its pocket) and each file's colour and label (`looks`). Then `send_ask` sends it with `says`, what the model says the sheet shows: on both real runs it described the design it meant, not what a bench picture showed. A file changed in between is refused, and a new `ask` replaces the drawing. Whatever the question says, the harness reads each settled need's check and `thin` against the sheet's files as they stand, and any that fail go beside the question in `question.md`, with what the bench says it drew and any need swapped since the last stop. On `cup-1` a question said a pane was split where `capture` read one. The process then exits. A person relays it, writes `pick.json`, and runs `resume`. A pick with no reason is refused, since the reason is what's learned from. After `needs`, `questions` is refused.

**A pick is about the look.** A build fault found at an ask goes in `"fix_first"` in `pick.json`, apart from the pick: it reaches the model as its own message, is `picks.fix_first`, and is an intervention of its own kind. On `cup-1` the Sponsor was asked to answer `none` for one, which mixed two answers. The pick still holds only for the files it saw, so the fix means asking again.

**A fix-first holds the fault, and its suggested way stays a suggestion** (mqucifer/print-shop#175, `faults.py`). On `eval-organic-3` a stand-in's fix-first named three faults and suggested a way for each. It reached the model as one text, and each compaction quoted it again, so the model read each suggestion as an order, down to its verb: "they explicitly said 'split'", and "The correct approach: DON'T fill… But the stand-in said fill." About 75 calls went on working round the wording, and it stopped twice to ask, though a merge or a moved line met every rule.
- **`fix_first` is a list of faults.** Each is `{"fault": what must change, "at": where, "rule": the request line, need or bench check that reads it}`, and may have `"suggest"`, one way to fix it. Each gets an id, `F<ask>.<n>`. A fault with no `fault`, `at` or `rule`, or with any other key, is refused at `resume`. A plain string is still taken, as one fault in the person's words with nothing suggested.
- **The relay keeps the two apart.** The faults go under "To fix", each saying how it's held, and the suggestions under "Suggested, yours to take or leave", with: "Any fix that meets every rule will do. If a suggestion would break a rule, don't use it. Say which way you chose." A plain string is relayed as a fault with the same line.
- **A fault is held, a suggestion never is.** Where a fault's `rule` names a bench check of the run's toolset in backticks, such as `` `pieces check map.json` ``, `done` reads that check again on what its clean run left, with the bench's own verdict as the limit, and the fault stands until that reading passes: the round isn't met, and the reply names the fault, its check and what it read. A rule in words alone names no check, whatever word it starts with, so nothing reads it; `resume` says which is which to whoever resumed. Nothing reads whether a suggestion was followed. Each reading is in `rounds/n/faults.json` and a `faults_read` event.
- **The model says which way it took,** in `ways` at `ask` or `done`, by the fault's id. `done` is refused before anything runs until each fault that stands has one. The next stop, a question or the stop for approval, shows each fault under "Faults named to fix first": its words, its check as it reads now, the way the model said it took, and that a way was suggested, never the suggestion. A fault with no check is settled by that showing, as a person reads it there; one with a check only by its reading at `done`.
- **A suggestion is said once.** `state.json`'s `faults`, the record of what the person said (`state.said`), the last thing said and what a need may quote from a pick all hold the fault's words alone, so a suggested way can't be quoted again or settled as a need. Each compaction's note, and a conversation started again from the record, gives the faults that stand, with each one's latest reading and the way taken. `picks.fix_first` in the ledger keeps the list as it was written, as JSON.
- **A later fix-first takes the place of the one before.** A pick's `fix_first` is the faults that stand from that pick on: each fault that stood is dropped, an empty list drops them all, and a pick with no `fix_first` leaves them standing. The model is told, a `faults_dropped` event keeps it, and `resume` says it to whoever resumed, with any dropped fault whose check failed when last read. It's how a person lets go of a fault whose check can no longer be read, such as one on a file the fix took away.

**What's relayed says who said it** (mqucifer/print-shop#53). On `eval-choice-1` a stand-in's answers reached the model as "The Sponsor's answers", though `--from` named the stand-in, and the model then wrote "the Sponsor confirmed" in set-aside reasons, and on `eval-rings-2` "The Sponsor caught this" in a lesson. So answers, notes and send-backs name the person, as `--from` or `--by` gives it, and the words "the Sponsor" appear only when it was the Sponsor: "The Sponsor's answers", "Answers from a stand-in for the Sponsor (who)", "A note from the operator". **Answers at `questions` say who gave them,** `--from sponsor` or `--from "stand-in: <who>"`, as a pick does, or `resume` is refused. A note's `--from` is free, and is "the people running this" when nobody says. A conversation started again from the record says each note's sender too (`state.notes_from`). The ledger's `interventions.from_who` and `questions.answered_by` hold who, and the after-action review's index reads them from there. Answers from before this read as `relayed as the Sponsor's`, as they did. **Nor do the harness's own replies say the Sponsor before anyone has answered** (mqucifer/print-shop#59): `questions`, `ask` and `send_ask` say the question has gone out to the Sponsor or someone standing in for them, and the answer says who.

**A pick says who made it,** so someone else's can't pass for the Sponsor's taste in later training data. `pick.json` is `{"pick": "A", "reason": "...", "by": "sponsor"}`, with `"pick": "none"` if nothing's right, and `"fix_first": [...]` if there's a fault to fix, as above. Any other key is refused. Anyone else is `"by": "stand-in: a Claude builder"`, naming who. Anything else, or nothing, is refused. Text says "the Sponsor picked" only when they did: what the model's told, the reading, and `record/ROUNDS.md`. The ledger has it in `picks.picked_by`, and `summary.json` in `picked_by`. An empty `picked_by` says nothing of who it was.

`questions`, `ask` and `met` aren't endings: the run waits, and `met` is what it rests in until a person decides. A run from before approval was a stop that says `met` stays ended, and `resume` refuses it, as it does a `closed` one. **`resume` goes on after any other,** from the very message it stopped at, with `--note` adding a message, and `--from` saying who the note is from. A crash loses at most the last call's answer, and that call is made again. A conversation started from the record keeps the notes as well.

A conversation that won't fit even compacted starts again from the record, keeping the request, the answers, the needs, the facts, each check's latest tries and the files. Its reasoning is what's lost, and `restarts` counts them. A conversation also starts again on purpose (mqucifer/print-shop#150): where the end checks send the part back, and where a person's send-back says `--fresh`. Those don't count toward `restarts`, whose limit is for a conversation that won't fit. `state.json`'s `restart_kinds` has each one's kind, `context_full`, `end_checks` or `send_back`, and the call it came before; the ledger's `timeline` has the kind as the restart's `name`; and `summary.json` counts them by kind, so the evals can tell them apart. A restart from before this has no name, and was `context_full`. Before that, a newest turn too big to fit goes back without its reasoning (mqucifer/print-shop#78).

### A call that ends without acting (mqucifer/print-shop#47)

Across the 1,122 recorded calls of 12 runs, 15 ended with no tool call, 12 of them after 16k tokens or more of reasoning, and 10 sat in two loops: `suncatcher-2` from call 248 to 261, and `eval-tip-1` from 70 to 114. Long reasoning alone isn't the sign, as most such calls end in a tool call. What both loops lacked was something to act on: a choice the Sponsor could make, or a reply the model could believe. So the answer is a question, not a cut (the Sponsor, 2026-11-04).

- **It's asked what's missing.** The reply says how long it reasoned, in tokens and time, and that this usually means something is missing: a figure, a reading, what a check's reply means, or a choice that's the Sponsor's. Then: say what with `ask`, and `send_ask`, or end with `blocked`. It replaces `QUIET`, which asked only for a tool call, and after which `suncatcher-2` reasoned to the cap three more times. Where there's no `ask`, as in the after-action review, it's `QUIET` as before.
- **A second one soon after gets a request whose only tools are `ask`, `send_ask` and `blocked`.** `send_ask` is there because an `ask` only draws the sheet. Soon is `Limits.ask_within`, 15 calls, recorded on the run: inside the two loops a repeat came 1 to 14 calls after the one before, and the one gap outside them was 141 (`~/print-shop/proofs/m18-ask/quiet_calls.json`). On the records it would first have come at `suncatcher-2`'s call 251 and `eval-tip-1`'s call 84. It holds until the turn ends in a stop, through a resume from the events, and a call to any other tool meanwhile, but what's below, is refused (`ask_only`) and not carried out. It leaves room to measure (mqucifer/print-shop#86): once each, one `write` or `edit`, one `run` and one `bench` command are offered and carried out, each reply saying what's left, and a second is refused (`ask_only_spent`) saying to `ask` or end.
- **The lock never leaves a run with no way to stop** (mqucifer/print-shop#192). A lock is there to stop a loop, never to end a run that has a design to show (the Sponsor, 2026-11-20). Besides the asking tools and its one build, run and check, it leaves open what an `ask` needs at the run's stage, each as often as it's needed (`Run.stage_open`): at intake `questions`, `breakdown` and `needs`, so the plan stop can be shown; in the rounds `done`, and `needs` while a note has reopened them. A `read` of the run's own cut-reasoning notes below stays open too, and no other `read`. The reply that sets the lock, and each that says it still holds, names what's open; a call refused under it says it as well, and an `ask` refused for what it lacks, such as no breakdown or nothing shown, ends saying what's open for it and to end with `blocked`, saying what it lacks, if it can't go through. **An ending under the lock names the lock:** the `ended` event's `said`, and so the ledger's `stop` row and `state.json`, gains `lock`: the call that set it, what was open, each call it refused with its tool and why, and `missing`, what the last refused `ask` lacked (or that none was tried). The after-action review is told it with a `blocked` ending. *Evidence: a leg-joint eval (2026-11-20) was locked at intake; told to `read` its note, it was refused as ask-only and lost the design it had stated; its edit was refused as its one build was spent; its `ask` was refused for no breakdown, `breakdown` as ask-only, its `ask` again for nothing shown, and it ended `blocked` with a design it said was complete. A pocket eval (2026-11-12) ended the same way, in its own words: the plan stop "is gated on recording the breakdown … Those commands aren't in my available toolset" (lessons runs19-joint:6 and :7).*
- **A call cut at the answer's limit keeps what its reasoning settled** (mqucifer/print-shop#99). Its reasoning still isn't sent back, but the harness writes two things from it to `record/cut-reasoning-<call>.md`: its last drafted script, from its last fenced python block, unfinished or not, and its last stated design, the paragraph or list before that block, or, with no block, the last passage that states a design or a plan. Nothing in it is run; the model can `read` it. Where it holds a script, the reply says the call was cut while writing one, names the file, and says to write it with `write`, run it and read it on the bench, and doesn't ask what's missing. Nor does it set the lock above: a call writing a script isn't stuck. Where it holds none, the reply is as before, naming the file for the design. Evidence: `eval-pocket-4` and `eval-fan-5` each settled a design partway (55% and 66%), wrote the script in the reasoning, were cut off in it, and after the old reply started cold and closed with no part (`~/print-shop/skill-evals/gate-2026-11-10b/RESULTS.md`).
- **Nothing cuts a call or limits thinking.** The `quiet` ending is as it was.
- **Each is recorded:** a `quiet_reply` event with the call, its reasoning's tokens and seconds, the tools the next request offered, under the lock what else it kept open (`stage_open` and the readable `notes`), and for a cut call whether a script was found (`script`) and the kept file (`kept`); and a `timeline` row, `asked`, named `what_is_missing`, `ask_only`, or `write_the_script` for a call told to write its script. The after-action index shows each after its call, and the review is asked whether the question named what was really missing.

### What a run keeps of what it learned (mqucifer/print-shop#39)

- **A shrunk reply says what failed and why.** Compaction shrinks every tool reply but the latest of each kind, and it used to keep only the first line, which for a failed `run` or `bench` is `exit 1`. On `suncatcher-2`, 139 of the 253 replies it shrank said only an exit code, and after a summary the model couldn't compare its failures. Now a bench answer keeps its exit and its verdict line with the reason, a run its exit and its last error (or the last line it printed), and a `write` or `edit` that ran a script what the run did (`session.gist`, at most 300 characters a line). Measured on `suncatcher-2`'s events, replaying each shrink: 139 such replies before, 0 after, for 11,334 more characters over its 24 compactions (`~/print-shop/proofs/m18-loop/compaction-suncatcher-2.json`). What stays whole is as it was: each file's latest text, the latest `run`, `bench` and `done` replies, the newest turn, and what a person said.
- **`record/CHECKS.md` keeps each check's tries,** beside `ROUNDS.md`, written by the harness after every bench call from `bench_calls`: each check (its command and files), the need that runs it, and each try's call, the settings that differ from the need's command (or from its first try, where no need runs it), and what the bench said. A wrong command isn't a try. A conversation started again after `context_full` is given each check's latest 6 tries in its first message, and the system prompt names the file.
- **After a compaction, the next message restates each check whose latest try fails** (mqucifer/print-shop#45): the same list as the replies', each line's reason cut to 100 characters, and each part file whose last `thin` failed, in one form. `Session.after_compaction` asks the run for it right after compacting, and says it before the next call; nothing is said when nothing fails. Replayed at every compaction of `eval-tip-1` and `suncatcher-2`, it's at most 281 and 304 tokens by today's estimate, under the 376 the compaction study allowed (`~/print-shop/proofs/m18-hold/replay.json`).
- **A refused `edit` says how its lines differ.** Of the 18 `edit.closest` refusals on `cup-1` (11) and `suncatcher-2` (7), sorted line by line against every version of the file the events give, none was text that had moved: 8 differed only in indentation, 3 left lines out of the middle, and 7 had a word or a number that was never in the file (`~/print-shop/proofs/m18-loop/closest_by_line.json`). So the reply names the difference: `edit.closest.indent` gives each line's indent and the file's, `edit.closest.apart` the lines left out, and `edit.closest` each of the model's lines that isn't there beside the file's nearest, with the closest block as before. Both new reasons start `edit.closest`, so a count of those stays comparable.
- **A call cut off at `max_tokens` goes back without its reasoning** (mqucifer/print-shop#47). Its text and its calls stay, its `call` event keeps all of it, and the change is a recorded rewrite, after a snapshot so `transcript.rebuild` replays it. The newest turn's reasoning stays whole at compaction, so on `suncatcher-2` each of calls 258-261, cut off at 65,536 tokens, was resent whole: each prompt after compacting was 108k tokens, 63% of it that reasoning, and it compacted once a call for 2.2 hours. Replayed with the recorded answers, main's rule gives 23 compactions and this gives 19, none of them in 259-263.
- **An edited file is kept as one current copy** (mqucifer/print-shop#47). A file's latest text used to stay as its `write` or whole `read` and every `edit` since, call and reply: four of the seven refused edits after `suncatcher-2`'s compactions were on one file kept as a write and 25 edits. Now the reply to its last edit carries the whole file as the edits left it, numbered as `read` shows it, and the rest are notes. The copy is rebuilt from the conversation, each edit applied as `edit` applies it: held to every edit's reply on the 12 recorded runs, all 226 agree (`check_copies.json`). Where it can't be rebuilt, or an edit is in the newest turn, the text and its edits stay whole as before. Replayed on the recorded answers with the cut-off rule, the files' kept text goes from 21.4k to 12.8k tokens a compaction on `suncatcher-2`, and from 15.3k to 9.9k on `eval-tip-1`, and `suncatcher-2` compacts 16 times (`measure.json`). The recorded baseline for refused edits: within 10 calls after a compaction, 6 of 43 edits were `edit.closest` on `suncatcher-2` and 1 of 8 on `eval-tip-1`, against 1 of 38 and 0 of 15 elsewhere. The re-run evals are held to it.
- **A compaction's note can't become a file's text** (mqucifer/print-shop#47). On `eval-tip-1` at call 109 the model wrote a file whose whole text was a note, as earlier `write` calls looked after compaction. A `write` or `edit` with a line that is a note in `content`, `old` or `new` is refused (`compaction_note`), saying the file is as it was and `read` gives it. A refusal over moving the note out of the call: a compacted call stays a well-formed call of its tool, so it's never an example of a call without its text, and the refusal catches a note however it came, in a `write` or an `edit`.
- **Tokens are counted at 3.18 characters a token** (`session.CHARS_PER_TOKEN`), fitted on the 1,122 recorded prompts of 12 runs as `Session._chars` counts them: the median of each prompt's growth against its characters' growth, so the estimate reads as often low as high. 2.7 read the growth 21% high, and so compacted early. Whole prompts at 3.18 are within 6.2% at the median (`~/print-shop/proofs/m18-ask/fit_chars.json`). Compaction's line is drawn from the model's window, below.
- **What's to be said again after a compaction** goes before the next call: `Session.after_compaction`, which mqucifer/print-shop#45 set to the checks that still fail, and mqucifer/print-shop#78 to the whole note below.
- **An `edit` on a file that changed since the model had it whole says so,** and which call changed it: the harness keeps each file as the model last had it (its `write`, a whole `read`, or an `edit` of what it had), and after each `run`, `bench`, and run after a `write` or `edit`, which of those files changed. ### Compaction's line, from the model's window (mqucifer/print-shop#178)

The line was crew's 125,000, copied from `crew_org/session/conversation.py`, in a window of 262,144 tokens that keeps 65,536 for the answer: every run was cut to about two-thirds of what the model holds. On `eval-table-1` it compacted 13 times in 183 calls, losing detail of a large assembly each time. The Sponsor: "I would give them large contexts but focused expectations… Nothing I'm seeing says it should be limited."

- **The line is the window, less the answer's room, less a margin for the estimate** (`session.compact_line`): 262,144 − 65,536 − 8,000 = **188,608** tokens. A conversation is compacted before a call whose estimate is at it or over, and not before.
- **The window is read where the run reads the effort,** LiteLLM's `/model/info` for the run's alias: `model_info.max_input_tokens`, the least where deployments differ, at the start and again on every resume. For `crew-code-think` it's 262,144, the whole window, not the window less the answer (read by the operator, 2026-11-19). Where LiteLLM doesn't give it, or gives no more than the answer and the margin, it's `session.WINDOW`, 262,144. A `window` event says the window, where it came from, the answer, the margin and the line; the run's recorded limits hold the line as drawn, and `summary.json` has it as `compact_at`.
- **The answer's room is each call's `max_tokens`** (`Limits.max_tokens`, 65,536): the harness's own, since LiteLLM sets no cap on the answer. A call asks for that much, so a prompt over the window less it is refused.
- **The margin, 8,000, is the estimate's measured error.** Before each call the estimate is the last measured prompt plus the characters since at 3.18 a token. Replayed on the 89 recorded evals to 2026-11-19, it read under the measured prompt in 40% of calls; of 6,036 calls between compactions, by at most 7,667 tokens (p99 2,924), and the same 7,667 among the 2,136 estimated at 100k or more (p99 3,099). 8,000 is that rounded up, so a prompt the estimate reads low still leaves the answer its room. Right after a compaction the estimate's growth is the compaction's cut, and it read low by up to 15,086 (p99 10,513, on 316 calls), but those prompts sit tens of thousands under the line. Each `call` event now keeps the estimate it was sent at (`estimated`) beside its measured prompt, so the margin can be fitted again (`~/print-shop/proofs/m20-compact-at/estimate_error.json`).
- **A call refused as over the window is compacted and made again, once.** Where LiteLLM answers 400 and its body says the context or window was exceeded (`send.OverWindow`; the body is matched and dropped, never kept), or a 400 comes with the estimate at the line, the session records `over_window` (the call, the status, the estimate, the line, the window, and whether the server or the estimate said so), compacts whatever the estimate says, and makes the call again. A second refusal is `context_full`, which a run meets with a new conversation from the record. Before this, a 400 under the line ended the run `call_failed`. The ledger's `timeline` has an `over_window` row, the after-action index says it before the next call, and `summary.json` counts them.
- **`context_full`, the oversize rule and the floor are against the new line.** The figures below were measured at 125k: pi5's newest turns at calls 148 (141.4k) and 206 (125.8k), and suncatcher-2's at 193 (140.3k), are all under 188,608 before anything is withheld, so the newest turn's reasoning is withheld only past it. The highest floor after compacting, suncatcher-3's 122.9k (105.3k under the rules below), is 65k or more under it.
- **What a longer context costs is measured, not guessed.** Each `call` event keeps its prompt (`usage.prompt_tokens`), the estimate, its seconds and its stream's first chunk. `scripts/call_costs.py RUN...` reports, for a run, its calls, compactions, new conversations and refusals over the window, and by measured prompt in bands of 25k: the calls, their median and 90th-percentile seconds, the median seconds to the first chunk, and the median answer. The baseline at 125k is `eval-table-1` and `eval-organic-3` as they stood on 2026-11-19 (`~/print-shop/proofs/m20-compact-at/baseline.txt`).

### What stays true, and what a later call replaced (mqucifer/print-shop#78)

The class is facts lost, and room spent on what was replaced. The evidence is outside this repository: `~/print-shop/skill-evals/context-study-2026-11-08/findings.md` (52 runs, findings 3 to 5 and option (d)) and `pi5-s3-stretch-2026-11-08/REPORT.md` §1. Figures below are from `~/print-shop/proofs/m18-keep/`, whose README says how each ran.

- **The model keeps facts with `fact`.** A fact is a name, a short text with its figures (at most 600 characters), and `from`, the call it came from. Setting a name again replaces it, and an empty `text` removes it. `record/FACTS.md` holds them, written by the harness from `state.json`. Each goes whole into the restart message, every compaction's note and every resume. On a design run the model worked out which way the fan goes in, the context filled, the restart lost it, and it worked from the opposite picture for four hours; after another restart it measured the same parts again, 42 minutes in all.
- **A bought part's fact has a fixed shape.** Named for its file under `references/`, it gives `box`, `way_in` (one of `+x` to `-z`, as `clearance --slide` names them) and `held_by`: the bench's `--slide` answer (mqucifer/print-shop#76), or what will hold it until something does. A name holds one fact, so each bought part has one. `designing-enclosures` and the start each say what a fact is for, in two lines. A given part fixed in place and never fitted gives `box` and `fixed: true` instead (mqucifer/print-shop#86).
- **A person's question gets a fact as its answer.** A note or send-back that asks something, a question or a sentence opening with say, tell, explain, describe, state, name or confirm, has a line beneath it: what it asks, and to answer each with `fact`. A design run's note asked how a bought part is fitted, and no answer was ever written down.
- **Every compaction leaves a note,** even when nothing fails: on the same run two compactions left none. It opens with the failing checks, as before, or "Compacted. No check's latest try fails.", then the facts (or a line on what one is for), the needs the last `done` didn't find met and those no `done` has read, the stops, and what a person last said: what it asked, or its start. Only the latest note stays whole; each earlier one becomes a note, found by where it was said (a `compaction_note` event), or by its opening in a run from before.
- **Compaction drops what a later call replaced.** Only the latest `needs`, `ask` and `breakdown` keep their arguments whole; an earlier one keeps its short arguments (80 characters or fewer, such as an ask's `stop`) and the rest becomes a note saying what replaced it. A one-off script, a `.py` written once, never edited, run once and left since, becomes a note with its run's gist. The main scripts stay: any `done` names, and any changed at least 35% as often as the most changed one, the context study's rule, so until a script has changed three times nothing is a one-off. Replayed on the recorded conversations right after each compaction (`floors.json`), pi5's floor at call 138 goes from 109.5k tokens to 73.2k (the study estimated about 70k), eval-fan-1's highest from 123.4k to 98.8k, and suncatcher-3's from 122.9k to 105.3k.

Only if it's still over does the run end `context_full`. The fourth, suncatcher-3 at 298, was the floor, which the rules above lower by 17.6k. These were at crew's 125k line: none of the three sizes is over 188,608 (mqucifer/print-shop#178).
- **The restart gives each check's tries or points at `record/CHECKS.md`, not both.** With tries, it says there's no need to read `CHECKS.md`; with none yet, it says that's where they'll be. One run read 10.9k tokens of `CHECKS.md` and `ROUNDS.md` again after a 31.7k restart message that held the tries.
- **A switch trims past reasoning, off unless an eval's arm turns it on:** `start --trim-reasoning`, kept in `state.json` for every process of the run. When past turns' reasoning passes `Limits.trim_reasoning_at` (40k tokens with the flag; 0, off, by default), every turn but the last `trim_keep` (3) loses its reasoning, in one step, so the prefix cache misses once. Each change is a rewrite (`trimmed`), and a `reasoning_trimmed` event and `timeline` row say how many turns and the estimate either side. It's the context study's option (e), and nothing here turns it on.

### A description says which part it describes (mqucifer/print-shop#53)

The Sponsor, 2026-11-04: "The inventory being out of date though does seem like a bigger more broad area to get at." ### When the model is stuck, it's told plainly (mqucifer/print-shop#79)

Read across 40 long calls (`~/print-shop/skill-evals/long-calls-2026-11-08/SUMMARY.md`), going round in circles was the main or second cause in 32, a contradiction drove 7, and the model never reached for `ask`. Each rule below is fixed where its trigger is, in `stuck.py`, and says what it means and what to do next. Nothing cuts a call or limits thinking.

- **A note that reopens the needs sets every settled need beside it.** *Evidence: on `pi5-case-1` a stand-in's note reopened the needs and asked for the clip's catch past the fan's frame; the model's own settled need said the toes catch inside it, nothing set the two side by side, it sided with its need at call 217, and the note's three new needs were never sent (`pi5-s3-stretch-2026-11-08/REPORT.md` §2).*
  - A reopening with a note (`resume --reopen-needs --note`, or a send-back with `--reopen-needs`) or with a pick's fix-first, once needs are settled, is followed, after the note, by a message listing each settled need: its `what`, its check and limit, how it read at the last `done`, whether it's fixed and stays, and whether it expects an overlap with a given part. It's relayed as `settled_beside`, so it's an `interventions` row, and the terminal that resumed is told.
  - `needs` is refused (`not_marked`) until `against_note` marks each of those needs `kept` or `changed`, with a line on why, against the note: `{"fits": {"is": "kept", "why": "..."}}`, or `"kept: ..."` as text. Kept means its check and `what` are sent as they were, files following the part as `glass` declares it; changed means they aren't, or it's dropped. The refusal names each one left, with its words and check.
  - Until `needs` is taken, each `bench` and `run` reply (a `write` or `edit` that ran too) and each compaction's note leads with one line: "A note reopened the needs; send `needs`, with each settled need marked kept or changed against it in `against_note`." The reply's `detail` has `stuck.reopened`.
  - A reopening with no note, and a `none` at the plan, set nothing beside: nothing contradicts the needs, and sending none stays a choice.
- **A need that expects an overlap with a bought part asks why.** *Evidence: once `pi5-case-1`'s need expected `INTERFERE` with the fan, no bench reply could point at the overlap as the fault, and the model chased OCCT against the mesh for 22 minutes instead (REPORT §3).*

The refusal gives that command from the need's own files.
  - It stands only if a person accepts it at an `ask` given `overlap`, `{"need": ..., "command": ...}`. The harness reads the command on the files as they stand: anything but `INTERFERE` is refused (`no_overlap`), and the reading goes to the model and into `question.md` under its own heading. Any pick but `none` accepts it (`State.overlaps`, and an `overlap_picked` event); `none` points the model at `--slide` again. An accepted need is held to its id and command.
  - An overlap between the model's own files isn't questioned.
- **After a call that went round in circles, the next reply offers a way out.** *Evidence: on `pi5-case-1` the harness's nudge to `ask` came after a 30-minute call, and the next call re-ran the same bench check (REPORT §5); `pi5-case-1-98` read "the needs are settled ... ask" as no way out, reasoned 30k tokens and ended with no tool call (`long-calls-2026-11-08/reports/pi5-case-1-98.md`).*
  - The trigger is a call the recorder marks as a runaway (a `runaways` row: its reasoning repeats past `review_repeat_share`, or it hit the limit), or a call of 16,000 reasoning tokens or more (the long-calls study's line) that re-runs a check whose last try failed, on files unchanged since. A check is its command and the files it names, as `nudge.py` has it; unchanged is each file's hash as the harness last saw it (`descriptions.seen`), from a call no later than that try. A bench reply that is such a re-run has `rerun` in its `detail`, whatever the call's length.
  - The first tool reply after it, or the re-run's own, leads with: "Your last reasoning went over the same ground. Run one check that settles it, or `ask` with what you have." Its `detail` has `stuck.circled`: the call, why, and the try it repeats. Once a call.
  - A runaway that ends without a tool call gets the reply mqucifer/print-shop#47 gives it, which already asks what's missing.
  - The call itself is never cut: runaways are kept and reviewed (the Sponsor, 2026-11-02). Only what comes next changes. `Session.lead` hands each reply to the run before it's kept.

### A hold is read on the slide, before the plan (mqucifer/print-shop#86, mqucifer/print-shop#87, mqucifer/print-shop#90, mqucifer/print-shop#91, mqucifer/print-shop#92, mqucifer/print-shop#97)

The held part is the one the words name first, unless a verb such as "holds" follows it. Words naming one of the two alone say it's the one held ("the lid stays on") and name no bought part, so a bracket's "holds a shelf" or "the fan is held by the lid" isn't such a hold. An eye need on that hold is refused as a bought part's is, giving `clearance <holder's file> <held part's file> --slide <its way off>` with `HELD`, the files by the parts' names; no fact gives a printed part's way off, so the refusal says to name it, and that the held part goes last, to swap the two if it's the other way. An eye need on what the bench can't read, such as how firm a pull feels, stays. At the plan stop such a part waits for a first try and its slide as a bought part does; a reading of the two in either order counts. *Evidence: on a design run a lid's snap onto its base was settled by eye, and the slide, run once, read the lid overlapping the base where it lay.*
- **A breakdown's name is matched to a given file widely** (mqucifer/print-shop#97). Names are read from the latest breakdown's parts and joins. A name is a given file by its path, its file name, or its stem as words of the name, the stem's underscores and hyphens read as spaces ("plug body" for `references/plug_body.step`); a trailing digit may be left off where that names one file alone ("pane" for `references/pane_1.step`). Where one given file is left unmatched by every name, a name still unmatched that says it's given, "(reference)", "(given)" or "(bought)" in brackets or at its end, is that file ("box (reference)" for `references/base.step`; since mqucifer/print-shop#191 a part's name has no brackets, and `breakdown` offers "box reference", which reads the same). A name still unmatched is a printed part. A `fixed` or `loose` fact ends the wait wherever the breakdown names its part, printed or bought, and a refusal naming a part with no file names the given files, to name it by one if it's given, not to build it. A hold word with "not", "no", "nothing", "never" or a "-n't" up to two words before it in the same clause isn't a hold ("not a grip"), though words that say a part comes off still are when negated ("never falls out"). *Evidence: the batch 9 gate refused `ask` 13 times across three of seven runs, on "plug body", "box (reference)" and "pane (given)" taken for printed parts, a fixed box's fact never read, and "NOT HELD ... not a grip" read as a hold.*
- **A fixed given part's fact has no way in:** `box` and `fixed: true`, in place of `way_in` and `held_by`; both together are refused, and the fitted shape is as it was. *Evidence: `eval-lid-3`'s base box had two facts refused until it gave one.*
- **A bought part fitted loose is held by nothing** (mqucifer/print-shop#91): its fact gives `box`, `way_in` and `loose: true` in place of `held_by`. `loose` with `held_by`, or with `fixed`, is refused. Neither the plan's wait nor the eye-need refusal applies to it, and the plan's refusal, wherever it waits for a bought part's slide, says how to say so. *Evidence: `eval-sleeve-3` and `eval-plug-3` each waited at the plan for a slide that could only read `NOT HELD`, on parts loose by design.*
- **The plan stop waits for a held part's first try and its reading** (`hold_unread`): a part file of the model's, and a `clearance ... <bought part> --slide <way out>` reading on it unchanged since, by `state.geometry`. It names what's missing and the command, and, without a fact or where `held_by` says the part is fixed, how to say so with `fixed: true`. The reading, whatever its verdict, is in the ask's reply, `asked.json`'s `holds` and `question.md` under "What holds each bought part, as the bench read it". The start says so in two lines where something was given, and the system prompt and `ask`'s `plan` say it too. A part that holds nothing is as it was. *Evidence: both fan-in-a-pocket runs spent over an hour at intake on a clip before anything was built; their lessons, pocket-1:1 and fan-2:3, ask to build and measure.*
- **At intake, a hold read `HELD` says what comes next** (mqucifer/print-shop#92). Once a held part's slide reads `HELD` on its part file as it stands, that `bench` reply and each later `bench` and `run` reply at intake lead with one line: the hold is read, so next come `breakdown`, `needs` and the plan stop, and finishing such as edges and fillets is round work after the plan. It's gone once `needs` is settled, and `NOT HELD` doesn't get it; nothing at intake is refused for it. *Evidence: `pocket-3` read `HELD` at intake, then rounded edges for about 20 calls and 40 minutes, never sent `breakdown`, and was closed at 56 calls before its plan.*
- **A run building at intake is told what comes next** (`nudge.py`, mqucifer/print-shop#146; the Sponsor, 2026-11-15: a nudge, not a refusal). Once a run at intake has a part file of its own and has read it on the bench, that reply leads with one line: it has a part file read on the bench and no breakdown or needs, so write the `breakdown` and settle `needs` now, then show the plan with `ask` (where the request has a plan). It's said again each 8 calls, on whichever reply comes then, until the breakdown is kept; from the breakdown the count starts again, and after 8 more calls with no needs it asks for the needs. It stops when the needs are settled. A reply to `breakdown`, `needs`, `ask`, `send_ask`, `questions` or `blocked` isn't led, a given file under `references/` isn't a part, and where a hold has read `HELD` the line above is the one said. Nothing is refused: building at intake stays open. Each is in the reply's detail as `intake_nudge`, with the file, the call it was first read at and whether the breakdown was kept. *Evidence: `eval-neon-strip-2` was building from call 8, read its own part on the bench at call 35, and kept its breakdown at call 98, its needs at 113 and its plan stop at 121, 5 h 18 m in, with the design it was approved with (lesson runs13-neon:18). The 8 is from the `intake-stalls` runs' ledgers: where a run moved on, its steps were 15 and 8 calls apart, and the runs that stalled went 63, 49 and 21 calls with a part on the bench and no next step.*

### When a run says it's done: the way on, and the bend (mqucifer/print-shop#150)

mqucifer/print-shop#142 gave the bench `fit-on` and `bend`, and nothing made a run use them: a design run's lid was approved that could never be fitted, because nothing read its way on. The Sponsor, 2026-11-15: "we can force the run of these after things are delivered, add that to the learn ledger and send it back with the learnings. That's what I expected." So the harness runs them itself (`end_checks.py`). It calls the bench's commands and acts on what they say; nothing in it measures.

**When they run.** At `done`, once every need has passed and every standing check above, on the files the clean run left, before the stop for approval is asked. A person only sees a design that passed them, or one the run asked a person about. A run that holds nothing is read for nothing.

**The way on, for every held part.** The holds are the run's own (`holds.py`). A held part's slide, `clearance ... --slide <way out>`, names the file that moves, the files it's slid against and its way out: the slide a settled need runs, else the latest one the model ran, else, for a bought part whose fact gives its way in, that part against the model's own files. `fit-on <moving> --onto <the others> --along <way out> --from clear` reads it: `clear` starts where the moving part's box is past every other's along the way, and a step more. A held part with no slide and no way in, or a file that isn't a STEP, is said as not read, "can't tell".

**The bend, for every place `fit-on` reads `BLOCKED`.** The arm is found by the harness, not asked of the model (`bench/arm.py`, in the second image), from the place and the printed part's shape, on each printed file of the two:
1. A column through the place along its depth's axis is the material the place is in, from its front, the face the other part meets, to its back. The place is at the front, and the push is from the front toward the back.
2. The part between two planes, 0.1 mm in front of that column and 0.1 mm behind it, falls into pieces. The piece the place is in is the arm with whatever joins it to the rest: where one of the planes cut it, it's joined.
3. Along each of the other two axes, an arm has every such join on one side of the place. Its root is the plane at the end of the joins nearest the place, and its box is the piece past the root, 0.1 mm clear on every other side. Of two axes that give one, the longer arm is taken.

**It isn't found** where the depth isn't across x, y or z; where the place is at no one face of what it's in; where what's there is joined level with the place or on both sides of it, as a band held at both ends is; or where less than 0.1 mm is clear behind it. The reply says which, and the place stands as `BLOCKED`. Then `bend <file> --arm <box> --root <plane> --push <the place's depth> --toward <way> --layers <axis>` reads the arm, its layers along the axis `on_bed` gives the file.

**What each place comes to:**

| | When | |
|---|---|---|
| passes | an arm was found, and `bend` reads `OK` | |
| doesn't pass | a printed arm was found and `bend` reads `FAIL`, whether what pushes past it is printed or given; or, between two printed parts, no arm was found, `bend` had no answer, or the two overlap where the part sits, which no bend clears | the run is sent back |
| for a person | one of the two is a given, bought part, and no printed arm was read there: none was found, or `bend` had no answer | it isn't failed |

**A given part isn't bent as PETG.** A flexible strip pushed past a catch gives way itself. Where one of the two is a given part and no printed arm was read at the place, what has to give way is the given part: the reading says how far, and that a person judges it. It's shown at the stop for approval, and doesn't send the run back. **A printed arm that reads `FAIL` sends the run back whatever pushes past it** (decided through the operator, 2026-11-15): a rigid bought part forced past a printed clip that's over its limit is the run's design to fix. *Evidence: a design run's fan couldn't be fitted in its slide-in pocket for exactly this (design-runs:33).*

**When one doesn't pass:**
- **A lesson is written,** a candidate, a `verify` lesson by `the harness`, for the model's route, reviewed like any other. Its evidence is the call and each command with its reading, so a reviewer can run them again (`lessons R` shows them as `end check`), and its keys are `fit-on` and `bend` with their verdicts. One lesson for each failing pair of files and what it came to: a second send-back for the same writes no second.
- **The run is sent back by the harness.** `decisions` has it as `sent_back` by `harness`, with no approval, as none was asked, so it isn't taken for the Sponsor's. Its note says, for each failing place: where, how deep, which arm (its file, box, root and push), `bend`'s strain against the limit, the arm's back against the room behind it, and what would pass, each with the command that read it. The round isn't met, and the next begins.
- **The conversation starts again from the record** (decided with the Sponsor, 2026-11-15: "it doesn't need its whole history when it gets this feedback"). It's the path a conversation that won't fit takes: the request, the answers, the needs, the facts, each check's latest tries and the files, and none of the earlier calls' reasoning. The note is the first message after the start, relayed as from `harness`, and never as what a person last said. Until the checks pass, each compaction's note and each later restart gives it again.
- **The stop for approval isn't asked until they pass, or the run asks a person.** `ask` with `"end_checks": true` has the harness read them on the files as they stand and puts each failing place beside the question, under its own heading. Any pick but `none` accepts each failing pair of files: `done` no longer sends the part back for those, and the stop shows them as accepted, by whom and why. With none failing, that ask is refused.

**When they pass,** the `done` reply and `stop.md` show each way and place under "Each held part's way on, and what bends on the way, by `fit-on` and `bend`", beside `thin` and the curves check. Each reading is a `standing` row (`way-on`, `bend`), and `rounds/nnn/end.json` and `end/` keep them.

**A way the bench has no answer for** (`DISAGREE`, `NO ANSWER`, or the second image not built) is "can't tell", as `thin`'s is: neither a pass nor a fail, and shown at the stop.

**Not in it:** `fit-on` or `bend` as needs a run must have (a run may still use them, and the end checks run either way), friction, how well a snug fit holds, or how a snap feels. Those stay with a person or a test print.

*Made up, in the second image (`tests/cae_cases/make_fixtures.py`, `~/print-shop/proofs/m18-end-checks/planted/`):* a box with one snap clip, its arm 1.2 mm thick, and a lid whose band passes the clip's hook 0.6 mm deep. With the arm free for 8 mm, the arm found is the box `-4.1,-17.1,18` to `4.1,-14.9,26.1` from its root at z 18, pushed `-y`; `bend` reads 2.98% against 1%, `FAIL`, and the run is sent back with one lesson. With it free for 16 mm, the same from z 10, `bend` reads 0.59%, and the run stops for approval. A given strip pushed 0.3 mm past a catch on a channel's 2 mm wall, where `bend` reads `DISAGREE` on a wall that's no beam, is named for a person.

### A part built flat is placed where it meets given parts (mqucifer/print-shop#201)

A design run made a table's apron, whose stained-glass panel sits on a face square to y in the table's frame. The orientation only matters when it meets other pieces." `placing.py` holds the rules.

- **The part is built flat,** in its own frame, the glass along z, the way `pieces` builds a panel. Every glass reading reads it there, unchanged: `light`, `capture` and `pause` at `done` and at each stop, and the model's own. None of them names a given file, so none is placed.
- **How a run places it, and where the placement is kept:** in an assembly file, the one fact a furniture run already writes for where each part sits (`docs/bench.md`'s [assembly file](bench.md#the-assembly-file)). The part's entry gives its `turn` about the origin's axes and its `at`, and its `with` names the files that go with it, such as its panes: `{"parts": [{"name": "apron", "file": "apron.step", "layers": "z", "turn": [["x", 90]], "at": [0, -200, 400], "with": ["pane_1.step"]}]}`. Any kind of run may write one. The given parts need no entry: they're given where they sit. A run's assembly files are those its `load`, `fit-bed` and `--placed` readings named, latest first, then any other JSON file in `work/` that names parts with `layers` (`print_sides.assemblies`), and the first that places a file of the reading's is the one used. The model keeps no turned copy: two copies drift.
- **Every reading against a given part reads it placed.** Each bench command the harness runs, `clearance`, `fit-on` or `render`, that names a file under `references/` beside a file an assembly places is run with `--placed` and that assembly, unless it names one already: the model's own `bench` calls, so the hold's slide that the plan stop waits for (mqucifer/print-shop#87); each bench need's reading at `done` and `needs`' tries; the end checks' `fit-on` (the place it reads `BLOCKED` is turned back into the file's own frame before `arm` and `bend` read it); and the stop sheets, `ask`'s and the final one. The bench says in its reply which files it placed and how. The ledger keeps the command in the model's words, and the reading's numbers keep `placed`. A reading that names no given file, two of the model's own parts, is run as it's written, and so is a bench command a script runs itself.
- **The stop pictures show both:** a sheet row that holds a placed file is drawn with it placed among the given parts, and again under it, `NAME flat`, with only its placed files, as built.
- **A part with no placement reads as it does today,** and nothing is guessed. Where a frame `glass` declares is read against a given file, by a bench need or a reading of the model's, and no assembly places it, the plan stop, each `ask`, `done`'s reply and the stop for approval say so under "Frames read against a given part, and how each is placed", with the entry to write if it's built flat; and where its frame is placed and a pane of it isn't in its `with`, that too. The harness can't tell a frame built where it sits from one built flat, so it's said, not refused.
- **Not in it:** a reading kept from before the assembly changed is still taken as current at the plan stop, as only a part file's change makes it stale; a script's own bench calls aren't placed.

## Toolsets

The Sponsor, 2026-11-03: "id be concerned with adding things like light-path commands unles its just a tool option or something, not everything is going to be a stained glass print." So the core stays general, and a check for one kind of object comes in that kind's toolset: its bench commands, the measures its needs may use, and its skills (`rounds/toolsets.py`). It's the first step to a shared core with toolsets per domain.

- **The request's `## Kind`** names the kind, and a run with none, or with a kind that has no toolset of its own, has the core only: a `bench` call of another kind's command is refused, saying which toolset has it, and the `bench` tool's description, the `needs` tool's measures and the start's skills are the toolset's. The start says which toolset it is.
- **A run from before toolsets** keeps every command it had, its skills, and its needs as they were: its `state.json` has no `toolsets`, and its recorded commands are in the ledger by name.
- **Each command, sorted:**

| Command | Toolset | Why |
|---|---|---|
| `info`, `clearance`, `readback`, `rays`, `params`, `render` | core | any part has a size, fits, cuts, holes, parameters and a look |
| `thin` | core | every printed file is read by it, whatever the kind |
| `wall` | core | any part may hang from a hole, or carry a load through one |
| `pause` | core | an insert dropped in mid-print, a nut or a magnet, is any kind's. It reads a closed nut's pocket as it reads a pane's (`~/print-shop/proofs/m18-verify/pause-nut.txt`) |
| `capture`, `panes` | stained glass | they read a pane in its pocket, held by lips on both faces, which only this kind has |
| `light`, `thickness` | stained glass | what a person sees through a pane |
| `pieces` | stained glass | a panel as a piece map: traced from a picture, checked against glass-cutting rules, fixed a piece at a time and built into a frame and panes (mqucifer/print-shop#152, mqucifer/print-shop#153). It reads a map and makes the part, as `layout` reads a layout, so no need names it: the part it builds is checked by the others |
| `edges` | enclosure | a case's edges a finger meets, softened to the request's radius (mqucifer/print-shop#60) |

**The stained-glass skill**, `designing-stained-glass`, comes with its toolset, with its reference `checking-stained-glass` (mqucifer/print-shop#37). It's built to Anthropic's skill-authoring best practices, and its reader is the local model, so it says more than Claude would need: a workflow with a checklist from how the piece is built and the 2D layout through each bench check, run, fix, run again, with the request's stops in their places; each term (cell, pane, leading, pocket, play, opening, lip, and a lip before or after play) defined once; exact commands for the checks and open guidance for the design. It folds in lessons 1 (the 2D layout, the leading in one piece), 2 (heights named once), 17 (a lip per cell) and 20 (no sharp tips), in general terms. **It builds curves as curves** (mqucifer/print-shop#54, the Sponsor on 2026-11-05: "Build it right the first time with right tools"): the layout is numbers, Shapely checks them in 2D, and the solids are built from the same numbers with CadQuery's circles and arcs, each offset of a cell drawn again further in, never with `polyline` through Shapely's points. Where only a polygon will do it gives `quad_segs` and the error it costs. `cadquery`'s `building-curves-from-a-layout` has the same step for any part, and its errors reference the calls the runs reached for. **Its evaluations came first:** `tests/skill_evals/designing-stained-glass/` has the gaps from the three runs' records (`gaps.md`), six scenarios each with a request, its files and the behaviour expected (`evals.json`), and the fixtures, made from scratch (`make_evals.py`). Two carry print-shop's additions after a marker line (mqucifer/print-shop#54), `errors.md` and `sketch-extrude.md`, and the text above it still hashes to the measured text. A need's `at_least` and `at_most` hold its number by the bench's own rule, so a figure at its limit, to a millionth, passes in both.

**Each kind's required skills, whole in the start** (mqucifer/print-shop#61). On `suncatcher-3` the start named all 15 skills in one sentence, ending "Read one with `skill` when you need it", and in 325 calls `cadquery` and `using-the-bench` were never read. A read was lost at the next compaction, of 31, and was read again. So each toolset names the skills its runs must have throughout (`Toolset.required`): the core `cadquery` and `using-the-bench`; stained glass its own first, then those two; the enclosure kind (mqucifer/print-shop#60) `designing-enclosures`, those two and `ref-fdm`. The start gives each whole, between `<skill name="...">` and `</skill>`, in that order, and names the rest in one line, to read with `skill` as before (`skills.start_skills`). The start is a user message, which compaction never touches, and a new conversation from the record starts with it again, so they're there for the whole run. A `skill` call for a required one is answered with where it is in the first message, not a second copy that compaction would make a note. A run from before toolsets keeps its one line.

**From a picture: the piece map** (mqucifer/print-shop#152, mqucifer/print-shop#153). Where the request gives a stained-glass picture, the skill's additions give the order: trace, check, fix each flagged piece by its own flag, check again, build. A table gives each flag its fix, and the skill says a filter over every piece is not a fix: on the first test from a traced scene one opening over every piece turned 15 to 22% of a band's glass into lead. The run's script calls the bench's own commands (`from bench.cli import main`), so `done`'s clean run makes the part again from the picture (`test_a_script_of_fixes_makes_the_part_again`). Its reference, `reading-a-piece-map`, says what a map holds and how to read each reply. No model has run it yet.

**Shapes from pieces, and a look at what was built** (mqucifer/print-shop#61). Of `suncatcher-3`'s 35 runaways, 8 traced an outline point by point in their reasoning and 6 worked out how the frame's own pockets were built. `cadquery`'s additions after its marker line, and the stained-glass skill's, say to build every outline from simple shapes, joined, cut and offset, never a hand-traced list of points, and to cut a part with pockets through them with `render --cut` after each build, before reasoning about what it holds. The stained-glass skill's additions name `cadquery` and `building-curves-from-a-layout` as step 5's reading, and `bench layout` as how to read its 2D layout. The text above each marker line is unchanged: `designing-stained-glass` hashes to what batch 3's evals read (`tests/test_required_skills.py`).

**How a run finds its skills** is in `skill_reads`: each `skill` call, at which call and round, the name asked for and the file it read, or `found` 0 for a name its toolset hasn't got, with `how` `read`; and each required skill a conversation's start gives, with `how` `given` at the call it goes with. `runs.toolset` has the run's kind, commands and skills. A runaway's `lacked` names the skills given apart from those read and not read.

Looking a lesson up when a reading fails isn't here yet.

**Written from the events.** `records.py` takes a run's events one at a time, live or from the file, and a second reading adds nothing, so a table doesn't depend on when it was read, and a process that was killed catches up when it's next loaded. `read-back` does it for a run that ended, and only reads its folder. A run from before these tables reads back with less: a note's sender is only "the people running this", its time is its first call's, and who made a pick comes from `picks.picked_by`, never from the message's words, since a stand-in's pick was once told to the model as the Sponsor's. Nothing is backfilled where it wasn't recorded: `fix_shape`, closing words, chunk times, lost arguments, and a need's `source`.

**The ledger only gains.** Tables and columns are added on open, and existing rows stay. An older checkout may still be running against it, so nothing is added to a table it inserts into by position (`needs`, `readings`). `decisions` and `after_actions` were made again once (mqucifer/print-shop#32), as a close needs `approval` to allow none and SQLite can't drop a NOT NULL in place: in one transaction, every row copied, and each earlier review names the approval decision it followed. Older code inserts into both by name, and a review it writes has its `decision` filled when the ledger is next opened.

### Runaways are evidence

The Sponsor: "When we get these run-away calls or repeating itself constantly its almost ALWAYS has been some issue with its context or tool or skill not working well. So to me these are not throwaways - its the obvious spot to look for fixes first." **Nothing here cuts a call or limits thinking.** Crew's whitespace cut is still the only cut.

- **A tool call's arguments are kept as they arrive,** in `streams/n.jsonl`, on the disk before the next piece comes. It stays if they didn't all come whole. `calls.stream` has the chunks' times, the longest gap and how far the arguments got.
- **It can't keep what never arrives.** On one real run the arguments of a call cut off at the limit never arrived, and the likely cause is the server holding them back until they're complete, which hasn't been probed. If so, `tokens_unaccounted` on the row, and `tool_args_chars` of 0, are what show it.
- **A row in `runaways`** is a call with a `finish` of `length` or `runaway`, or whose reasoning repeats earlier text past `Limits.review_repeat_share` (0.5, recorded on the run). Repetition counts sentences of 25 characters or more that match an earlier one word for word, by characters, over calls with at least 2,000 characters of such sentences. Paraphrase isn't counted, so it's a floor.
- **`doing`** is what it was calling, with any path, and how its text and reasoning ended. **`lacked`** is the evidence code can give: the skills read and not read, the compactions so far, the last bench answer, the last refusals and the needs failing. What it really lacked is a reviewer's call, which `review_note` is for.

### Measuring a change without a whole run (mqucifer/print-shop#67)

An eval takes one to four hours, so "did this skill text help?" would cost a run. mrCAD (arXiv 2504.20294) scores every round as improvement toward a right answer, and replays one recorded round with the history fixed; it found models made the part worse on refinement rounds. Two tools do that here, from the records alone.

**A score for each round** (`scores.py`). A scenario's right answer is a JSON file of ranges, kept apart from its request, which is what the model reads:

```json
{"scenario": "peg-through-a-plate",
 "ranges": [
  {"id": "gap", "what": "the least gap round the peg", "command": "clearance",
   "names": ["peg.step"], "number": "pairs.0.gap_mesh_mm", "at_least": 0.3, "at_most": 0.8},
  {"id": "across", "what": "the opening's least width across", "command": "rays",
   "number": "levels.0.across_mm.min", "at_least": 8.0, "scale": 1.0}]}
```

- **Each range names what the bench reads:** a command, the files its command line must name (by file name, so `references/peg.step` counts for `peg.step`, and a copy such as `peg-lifted.step` doesn't), a number in its answer, and the range. A list's item can be picked by a key, `panes[file=pane_small.step].open_pct`, since a list's order follows the command line the model wrote. One end is enough. A range of no width, or with one end, gives its `scale`, in its own units; otherwise it's the width. An opening sized by its gap all round is two ranges, as here: `clearance` reads the least gap, and `rays` the width across.
- **`start --right FILE`** checks it, keeps it as `right.json` beside the run's records (outside `work/`), and in `right_ranges`. Each round is then scored as it ends, into `round_scores`. The scenario that shows the form in this repository is `rim-by-share`'s `right` in `tests/skill_evals/designing-stained-glass/evals.json`; the operator's other scenarios keep theirs beside their requests.
- **Each range's value is the bench's, read from the ledger:** at a round's end, a need's reading (`readings`), then the harness's own checks at `done` (`standing`), then the model's last bench call in the round (`bench_calls`). Before it, the round before's end; and before the first round, the last bench call before it began. Each value says which answer gave it. Where two answers read a range differently at one moment, the further counts. A range nothing read is `null`, and counts in no sum. Nothing is run, and nothing is taken from what the model said.
- **The figures:** each range's distance outside it, over its scale. A round's `distance` is their sum over every range read at its end (`read` of `of`). Its `improvement` is (before − after) ÷ before over the ranges read at both ends (`compared`): 1 is right now, 0 no change, below 0 worse. With nothing wrong before there's none, and `said` says so ("right before and after"). Its `kind` is `first`, `again` or `refinement`, from the phase of each round's last call, so a refinement round's improvement is what a note, a send-back or a pick led to.
- **`scores NAME`** prints every round's score and the phases, from a ledger it opens read-only, so it can score a run whose records are kept read-only. `--right` names a file other than the run's own, and `--keep` writes the rows into `round_scores`, each under the right answer's hash, so a corrected file's scores sit beside the first.
- **Batch 4's nine evals,** from copies of their ledgers (`~/print-shop/proofs/m18-replay/baseline/`): each of the eight with ranges ended its last round at distance 0. eval-lid-1's one round went from a seated lid, 0.0 mm (the model's call 11), to 0.25 mm of play, an improvement of 1.0; eval-count-1's from two openings to three, 1.0; eval-sleeve-1's four rounds read right throughout, while its needs failed on number paths `info` doesn't print, so its failures were the needs', not the part's. eval-fan-1 is judged by eye and has no ranges. Most runs have one round, as a round is a `done`.

**A replay of one call with one thing changed** (`replays.py`). `replay NAME N` rebuilds call `N`'s exact request with `transcript.rebuild`, makes one change, and sends it `--times` times (3 by default), since the model varies. It sends nothing to the Sponsor, runs no tool the answer asks for, and writes nothing in the run's folder: each replay is a folder of its own, `~/print-shop/replays/<run>/call-NNN/<label>/`, refused inside the run's folder or this repository. The changes:

| Flag | What changes |
|---|---|
| none | Nothing: the control, for how far the model varies on its own |
| `--skill NAME=FILE` | A skill's text, wherever the request holds it: given whole in the start, between `<skill name="NAME">` and `</skill>`, and each `skill` reply that read it |
| `--reply CALL.K=FILE` | The reply to the K-th tool call (from 1) the model made at call `CALL`, such as a bench answer reworded |
| `--skills-card FILE` | The start's required skills, from "The skills this work needs throughout" to the last `</skill>`, as a short card of their rules or whatever the file says. It's tested as it would ship, with each skill's full text on demand: an earlier `skill` read of a required skill, which pointed to the start, gives the text the start had, and a try that reads one is answered with it and goes on to its next call, until a call ends in anything else. A turn that reads one and calls anything more ends there, as no other tool is run |
| `--lesson FILE` | A lesson added under the start's lessons heading, which is added if the start had none |
| `--replace OLD NEW` | One exact text, everywhere the request holds it, for anything else: both are files |
| `--tool NAME=FILE` | A tool's spec, its description and schema, as the request offers it, from a JSON file: such as `needs` as a checkout gives it (mqucifer/print-shop#93). The messages are as recorded |

A change that finds nothing to change is refused, so a replay never runs as a control by mistake. Each try records the reasoning's length (characters, and tokens where the proxy says), the call it ends in (`build`: `write`, `edit` or `run`; `bench`; `ask`: `ask`, `send_ask` or `questions`; `other`, with the tools named; or `none`), its seconds and finish, which required skills it read with `skill` (`read_required`), and whether it's long: past 20,000 characters of reasoning (`LONG_CHARS`, the line the runaways were read at), or cut, or at its limit. A try that went on after a read under a card keeps each call's figures (`calls`), its last call's at the top, the reasoning summed over them (`reasoning_chars_total`), and is long if any call was. The recorded call's own figures come first, from its `call` event. `replay.json` has every figure, `README.md` a table, `request.json` what was sent, and `n.json` each answer. A failed try keeps only its kind and status, as an error's words can name the proxy, and the rest go on. It runs on the proxy as any call does, from a committed checkout, and refuses otherwise.

**The first replays are the operator's,** after the merges, recorded on mqucifer/print-shop#67: eval-fan-1's calls 3, 5 and 6 with a worked clip, eval-rims-4's call 6 and eval-edges-1's calls 39–40 with reworded replies, before and after mqucifer/print-shop#65's wording, and three or four long calls with the required skills whole against a short card. Here the mechanism is proved with the scripted model (`tests/test_replays.py`).

## Lessons

The first of the learn loop in code (mqucifer/print-shop#28, M18's "learning logic", ADR 0010's decision 5 as changed on 2026-11-02). Before this, the operator wrote lessons into a run's analysis and copied them into the next run's request by hand. On `cup-1` four were given that way. The two about how to build were followed. The one about checking held until a check got in the way, and then the check was changed.

**The model writes its run's lessons, after the approval or a close, while it still has its context.** `resume --approve` records the decision and ends the run as `approved`, then makes one more turn on the same session. `after_action.py` holds it, apart from `review.py`, which writes the folder a person prints from: the two never share a name, in code, in what the model's told, or in the ledger.
- The model is told the part is approved, with the person's note, and asked for its after-action review. The message lists the lessons it was given, at the start or read whole with the `lessons` tool, and the run call by call from the ledger: the tools each call made, each bench answer and its verdict, and each round's readings where the round ended. A lesson names its calls from that.
- **It sees the harness's record** (mqucifer/print-shop#40). On `suncatcher-2` the review missed the harness's part: replies cut to `exit 1`, the run hitting `context_full`, and that `blocked` was never weighed. So the index shows, at their calls, each compaction and what it cut (replies shrunk by tool, turns' reasoning dropped, texts made a note), each new conversation after `context_full`, and each refusal and failed edit (`refusals`), nudge and runaway. It's told that where the harness hid something, or a stop wasn't made, that's a lesson for the harness. On `suncatcher-2`'s record, read back through a copy of the ledger, it shows 24 compactions, the restart, both `context_full` stops, 7 failed edits, 6 other refusals and 14 runaways (`~/print-shop/proofs/m18-loop/index-suncatcher-2.json`).
- **It sees what people said, in their words:** each note, answer, pick with its reason, fix-first, send-back and the decision itself, marked `[said N]`. Before, the index named only each one's kind and sender. `people` weighs each one: whether it should be a lesson, which of the review's lessons it became, and why. Every one is weighed, or nothing is kept, and each is a row of `said_weighed`.
- **Near its limit, it goes on from the record.** `suncatcher-2`'s review ran on a conversation compacted many times. If the review's won't fit even compacted, it goes on in a new conversation from the record, as a run does, with the decision and the ask after it: the index is from the ledger, so it holds the whole run. The restart is in the timeline and `restarts`, and the review is recorded as ever. Nothing cuts a call, and compaction's line is the run's.
- Only `read` and `after_action` work in it: the files stay as approved.
- `after_action` takes `lessons`, each with its fix's shape, its kind (its area, below), the routes it proposes, its text, its calls and any readings and keys; `scores`, one for each lesson it was given: `used`, `not_used` or `in_the_way`, with the calls that show it; and `people`. Every call must be one the ledger has of this run, every reading one it read, every lesson given scored once, and everything a person said weighed once, or nothing is kept and it's told what's wrong. Each lesson it writes is a `candidate`.
- **The run stays approved, whatever happens.** A review that can't begin, with no key or no LiteLLM, is a row of `after_actions` with `not_begun`, and so is one that ends any other way. `rounds.py after-action NAME` tries again, and a reviewer can enter lessons by hand. Its calls have a cap of their own (`Limits.after_action_calls`, 30), only so a review that never calls `after_action` ends by name. Nothing cuts a call or limits thinking. The timeline has the review as its own segment, and the approval and a close are interventions of their own kinds, `approved` and `closed`.

### A run that ends without approval

A run that's `blocked`, stopped, cut off by a limit, or judged not to be going anywhere has the most to teach (mqucifer/print-shop#32). The Sponsor, 2026-11-03: "I do wonder if we've set it up where a failure is a valid place to stop. It still has learnings."

- **A person closes it:** `resume NAME --close --by WHO --note FILE`, signed `sponsor` or `stand-in: <who>`, with a note. It works on any run that isn't approved, closed or running: after any ending, or waiting at `questions`, `ask` or `met`. It's refused while a session runs under the root, by the same lock, so a run's process has to be gone first: `stop` it and wait for it to end. A close isn't an approval. It's a row of `decisions` of its own, `closed`, with its stop for approval if it was waiting at one, and the run ends `closed`, with what it had ended as in `was`. Nothing goes on from it.
- **Then the after-action review, as after an approval,** on the same session with only `read` and `after_action`. The model is told who closed it without approving it, how it had ended (the ending's name and what it said, or the stop it waited at) and their note. It isn't told the part is approved. It's asked what didn't work and why, what would have changed it (a tool's reply, a check, a lesson, the request or a stage), and what it would do first next time, and it scores the lessons it was given. A review that fails or can't begin is a row of `after_actions`, the run stays closed, and `after-action NAME` tries again. The decision reaches the model at the first try that begins. The review has its own cap on calls and none on time, so a run cut off by `model_time` is reviewed too. Its lessons are `candidate`s, as ever.
- **A check that keeps failing is nudged.** When a `bench` command fails 4 times on the same files, whatever its other arguments, without passing as a need checks it, its reply gains the nudge. It's said again at each try after that, until the check passes as a need checks it.
  - **What it says:** one line for each try since that pass, giving its call, the arguments that differ from the first try, and how the bench's verdict and its reason began. Then: show what you have with `ask` and ask for what you need, or, if it can't be done, end with `blocked` and a clear account, as a failed, complete run is a valid end and its lessons are asked for after. It's the newest bench reply, so compaction keeps it whole.
  - **What counts:** exit 3 (the command was wrong) counts neither way, and any exit but 0 doesn't pass. A pass starts the count again only if its arguments are a settled need's, or if no need runs that check. `suncatcher-2` passed `capture` at `--min-lip 0.25` after failing at 1.2, 0.35, 0.45 and 0.3, and its need runs it at 1.2, so counting every pass would have let the bending the nudge is for end it.
  - **A need's check with other arguments says so,** pass or fail: which need, each argument that differs (`--min-lip 0.25`, the need says `1.2`), and that `done` checks the need's command.
  - It's counted from `bench_calls`, against the needs as they stand, so a run resumed on this code counts what it did before. Each nudge is a row of `nudges`, with the calls it named. It's lines in a reply, never a limit.
  - **The 4** is from the five runs' records: of 41 runs of failures of one check in a row, 35 were 3 or fewer, and the 6 of 4 or more include both of `suncatcher-2`'s loops (`~/print-shop/proofs/m18-close/streaks.json`, and `streaks_needs.json` as counted here). Counted by the whole command, the `capture` loop is five failures of one each.
- The system prompt says the same where it offers `blocked`, and so do the refusals of `questions` and `needs` once the needs are settled. In five runs before this, the model had never called `blocked`.

**A reviewer checks each against the ledger.** For now that's the operator, who signs `--by "reviewer: <who>"`: checking lessons is the reviewer's own job, not standing in for the Sponsor. `sponsor` and `stand-in: <who>` are taken too. Picks and decisions don't take `reviewer:`.
- `lessons RUN` lists what the run wrote, each with what the ledger holds at each call and reading it names, then what it was given and how each was scored, and what its start left out. `lessons` alone lists every lesson. Either way it ends with what's waiting for a route, what to retire, the kept lessons with no kind of part, any too long for a start, and each kind's to fold into its skill.
- `accept` (`--routes R,R`, `--becomes B`, `--part-kind K`), `edit` (`--text FILE`, `--kind`, `--shape`, `--routes`, `--becomes`, `--keys capture:FAIL,thin`, `--part-kind K`) or `reject` (`--why`), each a row of `lesson_steps`.
- **A review gives each lesson its kind of part** (mqucifer/print-shop#155): `--part-kind K`, a kind as a request's `## Kind` names it and kept by its toolset's key (`Stained glass` is `stained-glass`), or `--part-kind general` for one that's for every kind. An empty `--part-kind` on `edit` takes its kind away. A kept lesson for the model with none is listed under "Kept for the model with no kind of part": it starts every run until it has one.
- **A lesson for the harness is never given as a note.** It's accepted only with what it `--becomes`: `refusal`, `bench_check`, `toolset_check`, `stop` or `harness`. One for the request alone becomes `request`.
- `lessons load FILE --by "reviewer: <who>"` takes a reviewer's steps from a file, in order, by the same rules: `{"steps": [{"do": "write", ...}, {"do": "accept", ...}, ...]}`, as `lessons.load` says. A step names a lesson by its key in the file, or by its number if it's in the ledger. It's all checked before anything is written, and refused whole if a lesson is already there. It's how lessons are entered by hand, and how the operator enters the first rows.

### A lesson from another ledger (mqucifer/print-shop#137)

A run is given the lessons of the ledger beside it. The Sponsor's design runs read `design-runs/ledger.sqlite`, and each eval round has its own `runs*/ledger.sqlite`, so a lesson learned in an eval reaches the Sponsor's runs only once it's in theirs. Written there with `lessons load`, its calls were checked against that ledger's run, which hasn't them ("the ledger has no call N of RUN"), and the only way through was to cite design-run calls that don't show it. On 2026-11-14 seven accepted model lessons from one eval, among them "a ledge must overlap its wall", couldn't be copied for that.

- **`lessons copy LEDGER ID --by WHO [--ledger FILE]`** reads lesson `ID` in the ledger at `LEDGER`, where it came from, and writes it into this one (`--ledger`, or the one beside the runs): its words, area, routes, keys and kind of part as they stand there, and its evidence that ledger's run and calls. Each call and reading is checked in that ledger, as `evidence` checks one written here, and nothing is written if one isn't there, or if the lesson has none: nothing lets a lesson cite calls that don't show it.
- **The ledger it came from is read, never written:** it's opened read-only, so nothing migrates or changes it.
- **It's a `candidate` here, whatever it was there,** with a step saying where it came from and its status there. A reviewer lets it through on this ledger's terms (`accept`, with `--becomes` for one for the harness), and then it reaches this ledger's runs as any other lesson does, "from `RUN`" naming the eval's run. One rejected where it came from isn't copied.
- **Where it came from is a row of `lesson_copies`:** the source ledger's path, the lesson's id, run and status there, who copied it and when, and what that ledger held at its calls as it was copied. A lesson is copied from a ledger once: a second `copy` is refused, naming the copy and who made it.
- **`lessons` shows a copy's evidence from the ledger it came from:** every lesson's line says which lesson of which ledger it's a copy of, and a section after them gives each copy with what that ledger holds at its calls and readings. `lessons RUN`, for the eval's run, lists the copies from it the same way. If that ledger has moved, it says so, and shows what it held when the lesson was copied.
- **A lesson's run needn't be this ledger's now.** `lessons.run` named one of this ledger's runs; a copy names the other's. The table is made again once when a ledger opens, every row kept, as `lesson_scores` was, and `write` and `load` still hold a lesson written here to this ledger's runs.

### Areas, routes and layers (mqucifer/print-shop#40)

**A lesson's kind is its area, one of the five** the batch was cut by with the Sponsor on 2026-11-03: `job` (understanding the job), `verify` (verification), `process` (process control), `memory` (memory within a run) and `loop` (the learning loop). The area says what goes wrong. "The learning loop is much like model training, and rounds are its data" (the Sponsor).

**Its routes say who acts on it,** one or more, each with its own delivery and score. The model proposes them, and the reviewer confirms or changes them (`lesson_routes`).

| Route | Delivered as | Scored by |
|---|---|---|
| `model` | text the next run is given: at the start, under its budget, its kind's lessons first and then general ones, the rest by the `lessons` tool, and a kind's lessons in its skill once folded in | that run's own review, as before |
| `harness` | an issue in the next batch, `promote`d when merged | the next analysis |
| `request` | a line in the request template the operator writes from | the analysis |
| `operator` | a line in the checklist below, for the operator and stand-in | the analysis |

- **Delivered:** `promote ID --as B --where W` records it on its route: `note` or `skill` for the model, `request`, `checklist` for the operator, or what it became in the harness. The listing says what's waiting to reach each route.
- **Scored:** `lessons score RUN ID --route R`, once it's delivered there. A lesson's status follows each run's latest score on each route since its latest delivery: the newest that says anything, `used` as `held` and `in_the_way` as `broken`. A correction replaces that run's earlier score, so a lesson whose only score was corrected to `not_used` is back to `given`, or `promoted`.
- **A lesson can move route.** Once it's built into the harness or folded into a skill, and a run's score after that shows it holding, its text stops being given at the start, with a step saying why.

**Lessons for the model come in layers, not all at once.** "We can't just dump everything in context" (the Sponsor, 2026-11-03).
- `start` draws from each kept lesson for the model that's for the request's kind of part, or general (`lessons.part_kind`: a kind, `general`, or empty for one no reviewer has sorted, which is given as a general one). It gives as many as its budget holds, as below.
- The `lessons` tool finds the rest, and any other kind's.
- One promoted `--as skill` lives in that kind's skill, and isn't given at the start or found by the tool.
- **Each is keyed to the checks it's about,** by command and verdict (`lesson_keys`): the failing bench answers and readings its evidence names, or the keys the model or the reviewer gives. They're there for a look-up at the failure, which is the next batch (the Sponsor, 2026-11-03).

**Lessons from before the five are sorted once** when a ledger opens (`lessons.migrate`), each with a step keeping its old kind: build lessons to the model, check lessons to the harness, lesson 10 to the request and the operator, lesson 13 to the operator and the model, and 14 and 19 to the model, as settled with the Sponsor. Each one's area is the builder's sort, for the reviewer to check with `edit --kind`. Then, once, each lesson's status follows its scores, each change a step: lesson 7, corrected from `in_the_way` to `not_used`, reads `given`. `lesson_scores` is made again, every row kept, so a score on a route that isn't the model's needn't follow a lesson given as text. On a copy of the real ledger every row is kept and reads back: 26 routes, 12 keys and 25 steps are added, and a second open changes nothing (`~/print-shop/proofs/m18-loop/migration-ledger-copy.json`, `read-back-ledger-copy.json`). A lesson of an old kind written later by older code is sorted when the ledger next opens.

### The reviewer's and the stand-in's checks

For the operator, at each review and each ask (mqucifer/print-shop#40). It's the checklist the `operator` route delivers to.

- **Check each candidate lesson against the run's analysis and against each person's note:** a finding in either that no lesson holds is a lesson missed.
- **Write a lesson that's missing by hand,** with `lessons load`.
- **Read a bench verdict before its picture.** On `cup-1` the stand-in gave a false cause, read from a picture whose check said FAIL.
- **Give the reference pictures at the start,** with `start --reference`, not after the first round. On `stainedglass-1` the Sponsor's intent arrived late, after the plan had been written without it. The other half of that lesson, reading the plan at the first write, is now the plan stop (mqucifer/print-shop#38).

**The next run starts with what was kept for the model.** `start` puts the kept lessons for the model (`accepted`, `edited`, `given`, `held`, `broken` or `promoted`, its text still given, as above) that its budget holds, as below, into the first message, after the request and its files, under `## Lessons from earlier runs`, each with its number, its area, the run it came from and who wrote it. `lessons.md` in the run's folder holds them as given, so a conversation started again from the record has the same, and `run_lessons` has a row for each. A lesson for the harness, the request or the operator alone isn't given.

### A bounded start, and the `lessons` tool (mqucifer/print-shop#155)

Before this, `start` gave a run every kept lesson for the model, oldest first, filtered only by kind of part, and almost none had a kind. In the design runs' ledger on 2026-11-17, 34 of the 35 kept for the model had none, so every design run started with all 34, about 16,500 characters, and the list only grew.

- **The order** (`lessons.to_give`): those for the run's kind of part first, then the general ones. Within each, the lessons scored `used` on most runs come first, by each run's latest score of the lesson's text, and any a run's latest score says got `in_the_way` come last. Among equals, the oldest first.
- **The budget** is `Limits.start_lessons_chars`, in characters of the lessons' lines as given, each with its number, area, run and writer. Its default is 6000, about a dozen lessons at the 485 characters those 34 average. `start --start-lessons-chars N` sets it for a run, and it's recorded with the run's other limits.
- **They're taken in order** while each fits in what's left (`lessons.within`). The first that doesn't fit ends them, so none is given ahead of a better one.
- **A lesson longer than the whole budget is never given at a start,** and the filling goes on past it: one such lesson mustn't empty a start. It's the only one passed over. The start's left-out line names it ("Lesson 12 is too long for the start: read it with its `id`"), its row of `run_lessons_left` says so with its length, and the listing names each under "Too long for a start", by the default budget, for a reviewer to shorten with `edit ID --text FILE`.
- **The start says how many it left out, and how to find them,** after the lessons: "2 more kept lessons aren't here, to keep the start short: 1 for stained-glass parts and 1 general. The `lessons` tool finds them...". `lessons.md` holds it as given.
- **A lesson is never dropped to fit.** One left out isn't given, so its status and scores stay as they were, and it's a row of `run_lessons_left` with why. `lessons RUN` lists them under "Left out of its start".
- **The model's `lessons` tool finds a kept lesson** (`lessons.look_up`). It only reads.
  - With `words`, each kept lesson for the model that holds every word, in its text, its fix's shape, its area or its kind of part; if none holds every word, those that hold any, most first.
  - With `kind`, those for that kind of part, or `general`. With both, both. With neither, the run's own: its kind's and the general ones, in the start's order.
  - The reply is short: one line a lesson, with its number, its area, its kind of part, whether it's in the start, and its fix's shape. At most 30 lines.
  - With `id`, that lesson whole, as a start gives one.
- **A lesson read whole is given to the run:** a row of `run_lessons` whose `how` is `tool`, so the after-action review lists it to score with the start's, and a reviewer can score it (`lessons score RUN ID`). Listing a lesson gives nothing. The call is in `calls` and the events like any tool's, with the lessons it found, or the one it read.
- **Folding a kind's lessons into its skill stays the main route.** The budget and the tool stop a run starting with everything; they don't replace the review. The listing ends with "To fold into a kind's skill": each kind's kept lessons its skill doesn't hold yet, by kind, with the skill's name. Once one is in the skill, `promote ID --as skill --where PATH` takes it out of the start and the tool, as before.

**Scoring and retiring.** Each run's latest score moves a lesson, as above. A reviewer can score again (`lessons score RUN ID`), and the latest counts. A lesson given twice and not used, or that got in the way, is listed for the reviewer under "To retire", and `retire ID --why` takes it out. Nothing retires one by code.

**Its statuses:** `candidate`, then `accepted`, `edited` or `rejected`, then `given`, then `held` or `broken`, then `promoted` or `retired`.

**The first rows** are the lessons of `stainedglass-1`'s and `cup-1`'s analyses, written by the operator, with `cup-1`'s scores. Their words come from the Sponsor's runs, so they're a file off this repository, loaded with `lessons load` after this merges.

**Not yet:** looking a lesson up when a reading fails (the next batch, by the keys above), runs with and without a lesson to measure its gain, promotion into skills by code, and the crew's lessons (M16).

## The refinement pass

After approval, the approved folder is sliced through Orca, and what Orca made of it becomes findings in the ledger (mqucifer/print-shop#51, M18's step between approval and the learn loop). It runs after approval only, never inside design rounds, and never touches the printer. No model is called.

```
scripts/rounds.py refine NAME --nozzle MM --filament [COLOUR=]NAME... [--machine M] [--process P]
scripts/rounds.py refined NAME
scripts/rounds.py proposal NAME ID --approve|--reject --by WHO [--note FILE]
```

The Sponsor, 2026-11-05: "It should use orca's cli to add pauses not raw gcode. Use what we can of orca at any point. Same with color setting by object." And: "The goal of it is feedback that we can learn from. Part of that feedback could be part changes that need approval first." Printability is a second pass on an approved file, never a reason to fail a design.

**What Orca's CLI does** (2.4.2 on the Mac, `~/print-shop/proofs/m18-refine/cli-probe/`, each tested):
- **A pause:** `--load-custom-gcodes` takes Orca's own `CustomGCode::Info` as JSON, a `PausePrint` at a `print_z`. Orca writes `;PAUSE_PRINT` and the machine profile's pause G-code (`M600` on the Centauri). It puts an item on the nearest layer, a tie going to the lower, and runs it before that layer prints. So "pause after layer 13" on 0.2 mm layers is `print_z` 2.8. One file applies to one plate.
- **A filament and colour by object:** `--load-filaments` and `--load-filament-ids`, one id per file. Each filament needs `filament_colour`. The store's composed profiles have none, and with two filaments and none, Orca crashes (SIGSEGV), so the pass sets it from the file's colour.
- **Placement:** arrange turns parts unless `--allow-rotations=0` (its CLI starts it on; `--allow-rotations 0` exits 254). `EXCLUDE_OBJECT_DEFINE` says where each object went.
- **Warnings:** only in the log on macOS (`result.json` is written on Linux only), read with `--debug 3`.
- **STEP:** refused (exit 250). So each STEP file is meshed in the bench's image at Orca's own GUI defaults, 0.003 mm and 0.5 rad, and the mesh's volume and box are held to OCCT's. The operator's call on the issue (option A); the meshing is one seam.

**What it does,** for each folder of the approved result:
1. **Plates.** The largest file is the frame, on a plate of its own with its pause. A file inside the frame's box, above its underside, is a pane, set in at the pause. The panes and any other files print on a plate of their colour, as the printer has one filament loaded at a time. Each plate has its own filaments, from the store, on the Sponsor's textured PEI plate.
2. **The pause.** The bench's `pause` on the frame, at the process's own layers, with each pane as it sits (its mid-height and thickness). With no pane file, the inputs come from the run's own last `pause` call. Orca is given the layer it reads, and writes the pause itself.
3. **What Orca says,** first: its warnings; where it wrote the pause, against the bench's layer; each pane's first layer over it after the pause, with Orca's labels (on our frames, `Bridge` and `Overhang wall`: Orca doesn't know a pane is there) and how far it's laid above the pane's top; anything printed inside a pane's outline above its floor before the pause; bridges and overhangs; gap fill and the narrowest line; time and filament for each plate.
4. **The pass's own reading,** last: each layer's section of the part against every line Orca laid there, in the image. A stretch of the part with no line, at the part's edge, is `bare`: on the probe a 0.5 mm bar got no line on layer 1. Two wall lines laid over each other, more than 0.15 mm across, are `walls_overlap`: the same bar got one 0.42 mm wall down each side from layer 2, 0.34 mm over each other.
5. **Findings** go in the ledger, each with what it read, where (file, plate, layer and z), what it means for the print, and whose reading it is. Where none needs the part to change, the print steps are the pass's own: written into `refinements/n/README.md`, and into the run's `review/README.md` above the model's words, which stay marked as the model's.
6. **A finding the bench failed, or that needs the part to change, is a candidate lesson** (mqucifer/print-shop#59), for the model, keyed to its check and verdict, written by "the refinement pass", with the finding as its evidence. On `eval-rings-3` `pause` failed on 0.5 mm of air over the pane, which the Sponsor calls an unacceptable overhang over a laid-in pane; the part needed no change by the pass's reading and nothing was proposed, so it reached no one. A reviewer lets it through, or not, as any lesson.
7. **A proposal,** where a finding needs the part to change. Today that's a pane standing above the last layer before its pocket closes: raise the ceiling to the first layer line over the pane, at the cost of the top lip. Where the design's script has the ceiling's z or the pocket's depth as a top-level number, it's checked: `params --keep` re-runs the script with it in the bench's container, the run's bench needs are read on what it made, then `pause`, then Orca again. **A number counts only if it moves the ceiling alone** (mqucifer/print-shop#59): on `eval-arcs-1` the pane's thickness equalled the pocket's depth, so the try thickened the pane and failed its need. A try that changes any file but the frame, or leaves the ceiling short of the proposed height by `pause`'s reading, is passed over, and with none left the proposal is words, naming what each try moved. Otherwise it's words with the measured reason. Either way it waits: `proposal ... --approve|--reject`, signed as any decision. Nothing in the approved folder changes.

**By kind, and on the side the run names** (`refine/kinds.py`, mqucifer/print-shop#66). On `eval-lid-1` every row spoke of a frame and panes ("no pane sits in the frame, and the run never ran `pause`"), and the lid printed as stored, lip down, with 6.2 m of bridge at z 5.2; on `eval-plug-1` a 2 mm plate stood on its edge, 99 layers with 2.2 m of gap fill; on `eval-fit-2` the given pane wasn't in the approved folder, so no pause was set.
- **The side on the bed is data.** `done` takes `on_bed`, each file's side as the script stores it, `-z` (as stored) to `+y`, kept in the stop's review record and said in its README. The bench's mesher turns the file whole in OCCT before meshing, so the mesh is still held to OCCT's volume and box, and says how much of it touches the bed. A side with under 1 mm² flat on the bed, or a frame a pause is read on, prints as stored, said with why. A file with no side named prints as stored, and that's said too; since mqucifer/print-shop#192 `done` names every printed file's side unless the request leaves it to this pass. Choosing a better side is still mqucifer/print-shop#9: this only honours the one stated. A bed need on the file is read on it as laid, in its `on_bed` finding (mqucifer/print-shop#73, above).
- **A kind says what's printed, what's context, and which events apply.** An enclosure, or any kind with no plan of its own, has no frame, no panes and no pause: each file on a plate of its colour, its `refine_files` role `part`. Stained glass takes its frame and panes from the run's last `glass`, not from where files sit: a given pane `glass` names is read as it sits, from the run's `work/references/`, for the pause and Orca's lines over it, and never printed (role `context`). With no pane file to hand, the pause is read at `glass`'s own `pocket_z` and `pane_thickness`. A run from before kinds reads as it did. A pause the bench fails is given in the print steps with the bench's reason beside it.
- **Gap fill inside a wall is named by its cause** (mqucifer/print-shop#65 item 5, carried here). The bench's `cover` reading measures the part's width at each gap-fill line, twice its way to the section's edge. Where gap fill lies inside a wall over 5 layers or more at one width, a `gap_in_wall` finding says what the profile's walls a side take of it, twice their spacings (each line's width less a layer's `h × (1 - π/4)`, from the process's `outer_wall_line_width`, `inner_wall_line_width`, `wall_loops` and `layer_height`), and the widths either side that print with no gap fill and with infill. Whole lines aren't the rule: swept through Orca at the Rapid PETG 240° profile (mqucifer/print-shop#65, `~/print-shop/proofs/m18-bench/walls/walls.json`), a wall is clean to 1.66 mm, gap-fills from 1.68 to 2.26, and takes infill from 2.28, so both 1.80 and 2.25 gap-fill. The two edges aren't a figure of the profile that one profile shows, so the pass asks Orca (`refine/walls.py`): it slices a test wall, a square tube, at the plate's own profile, from the part's wall outward in 0.1 mm strides to the nearest edge each way, bisected to 0.02 mm, about a dozen slices of half a second. At the store's profile real Orca gives 1.66 and 2.28 (`tests/test_refine_orca.py`), and from each of the sweep's 30 gap-filled widths the search finds the same pair. On a copy of `eval-edges-1`, real Orca and the bench image: "2.00 mm wall: its 2 walls a side, 0.42 mm outer and 0.45 mm inner lines …, take 1.57 mm of it … By Orca's own slices of a test wall at this profile, a wall prints with no gap fill up to 1.66 mm, and takes infill from 2.28 mm", over 13,640 of its 14,267 mm of gap fill, layers 10 to 96; layers 97 to 100 are its half-round rim, narrowing from 1.90 to 0.86 mm, and aren't a wall of one width.
- On copies of the evals' records, with `on_bed` as the closing words named it (`~/print-shop/proofs/m18-refine/batch5/`, real Orca 2.4.2 and the bench image): `eval-lid-1` prints its plate on the bed, 2,400 mm² against 281 as stored, and the bridge at z 5.2 is gone; `eval-plug-1`'s wall prints 2 mm tall, 498 mm² on the bed against 60, with no gap fill and no overhang over the opening; `eval-fit-2`'s given pane sets the pause after layer 11, Orca and the bench agreeing, where `pause` fails it on 0.5 mm of air over the pane.

**Checked against the record.** On copies of the approved runs from 2026-11-04 and 2026-11-05, the bench and Orca both pause after the layer the record holds: `eval-hanging-2` after 13 and `eval-rings-2` after 11, as `scores.md` has them, and `eval-light-3` after 14, as its own last `pause` read (call 47 in its ledger; its folder has no pane file, so that call gives the inputs). On `eval-hanging-2` Orca leaves layer 14 open, where `pause` closes it (the pocket's ceiling is on that layer's mid-height), so its first layer over the pane is 0.3 mm above it, not 0.1: said, with both readings. `eval-rims-2` and `eval-thick-2` were never approved, and the pass refuses them.

**Not here yet:** supports, and choosing an orientation (mqucifer/print-shop#9), the model proposing settings (mqucifer/print-shop#13), and the model at all: its place comes once there are findings to learn from. A proposal approved isn't applied by code: it goes to the design, as a new run or a send-back.

## Where each part came from

The session is ported from mqucifer/model-performance's `cad_eval` at 22ea8b7, not imported, and nothing here imports crew. A shared core is extracted only at a second or third real use.

| Here | From | Changed |
|---|---|---|
| `session.py` | `session.py`, the base arm | It outlives its stops, every tool call in a turn gets a reply, a call is retried, and `restore` reads it back |
| `tools.py` | `tools.py`: `write`, `edit`, `read`, `run`, `lookup`, `docs`, `skill` | Adds `bench` and `lessons`, and `read` shows pictures. `edit` keeps crew's `replace_text` rules |
| `paths.py` | `inside`, `open_inside`, `copy_plain` | Unchanged in what they refuse |
| `send.py`, `transcript.py` | `send.py`, `common/litellm.py`, `transcript.py` | `snapshot` events |
| `needs.py` | The idea of `plan.py`: a quote held to the source | Needs, not a plan |
| `judge.py` | `final_case` | A bench command per need, not hidden checks |
| `bench/search.py`, `bench/hint.py`, `bench/image/*_index.py` | The same files | Started by `host.helper`, not on stdin |
| `skills/cadquery`, `skills/references` | `skills/` at 98b3c5b, byte for byte above any addition of print-shop's, held by a hash and a test on the Mac | `skills/bench` is new. Where they say `inspect` or `measure`, the system prompt says what those are here |

**Lessons carried, and how:**
- **A link made in a container resolves on the host.** Each host-side open walks from the directory's fd with `O_NOFOLLOW`, and takes only a regular file. Tests make the links in a real container.
- **A process left by a run could race the harness, or plant a `python` on its PATH.** Each command here is its own container, gone when it ends, with `/work` on no PATH and `python -I` for every harness command. So there's no reaper, and a test holds that a `setsid` daemon doesn't outlive its run.
- **Runaway calls aren't a client timeout.** Calls are streamed, and crew's whitespace cut is the only cut.
- **Compaction lost the script once.** Each file's latest full text stays whole, and only a whole `read` counts. Here the latest `bench` and `done` replies stay too, what the Sponsor said is never touched, and a shrunk reply keeps what failed and why.
- **No address in the records.** LiteLLM's api-base header is dropped.

**Not ported:** `plan` (a gate on one-round evidence, and the needs say what's wanted), `measure`, `inspect` and `view` (the bench answers those, with second checks), the hidden checks and the arms. The per-call comparison of serving with infra's record (`identity.py`) is left out: a call's `x-litellm-*` headers are kept, for comparing later.

**New limits, found building this:**
- A script that prints without end would have filled the Mac's memory and Docker's disk through its log. Only the end of a command's output is kept, and containers have no log.
- `/work` is a folder on the Mac with no quota. A file is capped at 2 GiB, and `work_gb` ends a run.

## The first real run

On 2026-11-01, `crew-code-think` through LiteLLM, on a made-up LED tealight stand, with a Claude builder standing in for the Sponsor at the pick. Commit e8ab52a, image `sha256:c950cbb83857`, with a crew tick running as it started, so no timing claims. It went from intake to `met` in round 1: 37 calls, 2,918 s of model time. Its figures are in `~/print-shop/design-runs/tealight-1/summary.json`, and its readings in the ledger. One run on one small part, so it sets no limit either way. mqucifer/print-shop#17 has what it did and what it lacked. Fixed from it:
- **`run` lost what a stopped script had printed,** since Python buffers its output into a pipe. A 600 s hang came back with nothing. Containers now run unbuffered.
- **A need's check couldn't be tried before it was settled,** so the model guessed a number's name. `try: true` reads them.

mqucifer/print-shop#19 then took what else it lacked: close-ups, sheets of the part alone, and a pick that says who made it. **Its pick is a stand-in's, a Claude builder's, and isn't the Sponsor's taste.** Its records were corrected on the Mac: `picks.picked_by`, the reading's `why`, `pick.json`, `state.json`, `judgement.json` and `ROUNDS.md`. `events.jsonl` is left as it was sent, since it's what the model was told and every request rebuilds from it, and a last `correction` event says so. Anything reading it for training reads that event.

**Known limits it showed:**
- **A need is only as honest as what it's checked against.** Here the fit's checked against a tealight the model drew from the request's numbers. That's right on this part, but no code holds a fixture to the request.
- **The pick wasn't held to the final part.** An eye need passed on the pick, and nothing compared what passed at `done` with the variant the Sponsor picked. Here the two read the same volume by the bench, and that comparison was by hand. mqucifer/print-shop#24 holds a pick to its files.
- **A design made before `needs` is round 0.** `bench_calls` holds its readings with round 0, and `rounds` starts only at `needs`, so here one "round" follows 32 calls of real design work.
