# A part's settings studied

mqucifer/print-shop#339. The Sponsor, 2026-11-26: "I was hoping that the model could go through a couple of different iterations of infill or other strength settings to try and see where the trade off between strength, material use and time is ... depending on print orientation different infill will have a different impact. ... Today it's just spitting my defaults back at me."

So the print loop's model (`setup.model.setup_llm`, through LiteLLM :4000) studies a part's settings with tools, as the print loop chooses a pose (mqucifer/print-shop#129). It isn't a fixed sweep: it reads where the part is stressed and which way, chooses candidates for that stress, goes on where the trade-off is still open, and recommends one against the profile's own. **Nothing is printed, armed or sent to the queue.** The table and the recommendation are for the Sponsor at the gate.

It builds on two pieces: regions of a part's own settings sliced through Orca's own modifiers (mqucifer/print-shop#341, `slicer.regions`, `slicer.joints`) and `load` reading a part as printed (mqucifer/print-shop#342, `bench.as_printed`, `bench.infill`).

## Running one

On the Mac, with Orca installed and the bench's second image built (`scripts/bench.py build cae`):

```
uv run python scripts/settings_study.py run PART.stl --assembly A.json --part NAME \
    --nozzle 0.4 --filament "Elegoo PETG" --turn 0,0,0 \
    --case 'standing=--weight 30 --at 10,10,700' --case 'lifted=--lift top' \
    --out ~/print-shop/design-runs/RUN/studies/NAME
```

- **`PART.stl`** is the part in its own file's axes: the same solid as the STEP file the assembly names for it, which `load` reads. The regions are in those axes, so both sides read them alike.
- **`--assembly`** is what `load` reads the load cases on, and **`--part`** the part's name in it. A part's loads come from its own design run's load cases, read on the part alone with what holds and loads it, so it reads in one pass: a printed part read in two passes has no answer yet (below).
- **`--turn`** is the pose it prints in, `RX,RY,RZ` in degrees, and must stand the assembly's `layers` axis up. Its turn about z, the part's up axis, may be any angle (mqucifer/print-shop#351): a long part that fits the bed only turned on it is studied as `0,0,35.5`, say, or as `0,0,fit`, which takes `fit-bed`'s own turn, the least that fits its footprint on the bed (`bench.footprint`). The turn leaves the layers axis as it is, so `load` reads it as before; the regions stay in the part's own axes and turn with it, and so does `infill_angle` on its way to Orca's plate angle. A pose that doesn't fit the bed is refused before Orca runs, saying the turn that fits it, or where none does in any pose, its least footprint. The model may read another pose where that changes what the layers carry, each that fits turned the same way; `load` is then told the layers' axis that pose gives.
- **Each `--case`** is a name and `load`'s words after the assembly file. Each case's name is its own, of letters, digits, `.`, `_` and `-`: the table's columns and each case's `load` replies are keyed by it, so two of one name, between `--case` and the needs' ids, are refused. Or `--needs RUN/record/needs.json` takes each `load` need of a design run as a case (only `--need ID`'s, where given), with the need's own figure and limit (`moves_mm` at most 3, say) besides the material's; the run's assembly word is replaced by `--assembly`, and its `--out` left out.
- **`--context`** is a sidecar or a design run's folder, for the part's fits (`setup.context`): a region can be put round each.
- **`--out`** is where it writes: `study.md`, the table and recommendation for the gate; `study.json`; and `candidates/NAME/` for each, with its Orca project (`regions.3mf`, or `part.3mf` where it has no regions), its G-code and each case's `load` reply. Without it, a new folder under the system's temporary one. Keep a real part's study with its run's records, off this repository.

**Each candidate in Orca, by eye** (mqucifer/print-shop#357). `study.md` links each candidate's Orca project in its row of the table, and the recommended one's under the recommendation, by its path from `study.md`'s own folder: `candidates/c2/regions.3mf`. It's Orca's own project, the part posed as it was sliced and its regions as Orca's own modifiers, with the candidate's settings in it. Open it in Orca with File > Open Project, or from the study's folder, `open -a OrcaSlicer candidates/c2/regions.3mf`; each region is a modifier under the part in the object list, its settings beside it.
- **`--ledger`**: the Mac's ledger unless given. `--max-candidates` (10) and `--max-hours` (6) are the loop's limits.
- **`--reserve-memory`** and **`--reserve-cpus`**: what of Docker's memory and CPUs is kept for other work on the host, a design run's bench or a builder's tests; else `BENCH_RESERVE_MEMORY` and `BENCH_RESERVE_CPUS` in the Mac's settings, else one bench command's own 3g and 2 CPUs. **`--serial`** reads one slice or `load` at a time, as before, and only here. **`--here-only`** reads only on this host, not on the remote hosts the settings name (below).

A candidate is two slices and a `load` for each case, about a minute each on a small part, and a leg's longer. The model's calls are limited too (`study.loop.MAX_CALLS`).

**Read in parallel, within the host's budget** (mqucifer/print-shop#364). The slices and `load` reads are independent of each other, so a study runs as many at once as the host holds (`bench.budget`): Docker's own memory and CPUs (`docker info`), less what's kept for other work, as above, and less what the VM itself had in use as the study began, measured (`/proc/meminfo` in a container, less what the bench's and the rounds' containers then used). As each read takes its slot, the memory limits of the bench's and the rounds' containers other processes are running (`docker ps`) are taken from what's free too, and a read waits for them. Each `load` holds its container's memory, 3g, or 4g for `load --parts` (`host.memory_for`), and its two CPUs; each slice, which runs on the host outside Docker with as many threads as Orca likes and no option for fewer, holds 3 cores, as measured: slicing a column 80 mm across and 200 mm tall, Orca kept 2.25 cores busy on average in rectilinear and 2.64 in gyroid.

**What's read in parallel is what's read alone,** within limits stated here. Each solve is single-threaded inside (mqucifer/print-shop#348). And each `load` reads in the passes its words ask for: one, or two with `--parts`, and is never offered the longer limit on which its own clock could take a one pass to two (mqucifer/print-shop#331), so how busy the host is can't change how it reads. A study's `load` is one pass anyway, as a printed part read in two passes has no answer. On the Mac, `load load/one.json --weight 5` of the CAE suite's fixtures, read three times two at once, read the same figures as it did alone, all but `mesh_s` and `solve_s`, the seconds each step took. The same study read with `--serial` and in parallel gives the same table (`tests/test_study_parallel.py`). What a busy host can change is time: a read that runs past its limit, as an Orca slice past its 900 s or a `load` past its 600, has no answer, as it would alone at that speed, which is why each job holds its cores.

**And on remote hosts** (mqucifer/print-shop#373). Where the Mac's settings name remote Docker hosts, a study's `load` reads run there as well as here (`bench/remote.py`, `bench/pool.py`); `--here-only` keeps them here. Each host is stated, and nothing about it is guessed:

```
BENCH_HOSTS=spark
BENCH_HOST_SPARK_SSH=spark           # the SSH target, as ~/.ssh/config names it
BENCH_HOST_SPARK_CORES=5-9,15-19     # the cores its jobs are pinned to, --cpuset-cpus
BENCH_HOST_SPARK_MEMORY=15g          # the memory its jobs may hold at once
BENCH_HOST_SPARK_FLOOR=10g           # the MemFree never to go under
```

- **A job there is a job here,** by the host's own Docker (`docker -H ssh://TARGET`): the same `docker run`, with the same limits, user and no network, pinned to two of its cores of its own. Its files go into a Docker volume of its own, and the bench's code at this checkout's state into another, mounted read-only where it is here. Nothing is written on the host's own disk or installed there. The reply comes back, and the files it saved come back into its folder. Its record names the host (`ran.host`, `here` or the host's name) and the cores it was pinned to, and its volumes are removed as it ends, however it ends. It runs each image by the ID checked here, never by a tag that may since have moved. It can't outlive its study: `timeout` kills it inside its container 300 s past its own limit, whatever became of the Mac. A study stopped by a signal (SIGTERM) ends as an interrupt does, stopping what it's reading here and there, and a study says any volume it couldn't remove as it ends.
- **It touches only its own.** Every container and volume it makes is `print-bench-` and a new id. Its containers carry their memory and disk by label, and its volumes their job and when they were made. Every run there is `--pull never`. It never asks Docker about anything else on the host: no `exec`, `inspect`, `logs` or `stop` of another's. It lists the bench containers there by name and label alone (`docker ps --filter name=print-bench-`).
- **Refusals.** A host whose images differ from this host's by ID, or lack one, isn't used, and the study says so as it begins (`scripts/bench.py send NAME` sends them). And a job isn't started there where the host's MemFree, read in a container of its own before each start, is under its floor plus the job's limit, plus what this study's other jobs there may take yet, plus the memory label of every other bench container there (another study's, or a run by hand; one with no label at 4g). A job holds its memory and disk there from its reservation to its end by a small labelled container of its own, so another process counts it whole while its files go over too, and the count is read again once its hold is up. MemFree, not MemAvailable: on a unified-memory GPU machine the GPU's memory is counted in MemFree. Nor where its Docker disk wouldn't keep the bench's 5 GB floor free with 2 GB for each of this study's jobs there, and each other bench job's bound by its label. The disk is read again every 30 s while its jobs run, and where it falls under the floor they're killed, the host takes no more, and each is read again elsewhere, said. A job whose /work came to more than 2 GB is said in the budget line. Before a study starts on a host, the volumes an earlier one left there are removed: only print-shop's own by label, older than the longest a job may last, whose job's container is gone, each one said. The job goes to another host with room, or waits.
- **Placed by budget and measured speed.** A `load` goes to whichever host has room for it now: its memory and cores free within the host's budget, and its free memory as above. Where more than one has room, the fastest for that case's command as measured, each host's seconds kept as its jobs end; a host not yet measured for a case is tried first, so it is. A slice runs only here, where Orca is.
- **Each candidate's cases on one host.** The same image by ID and the same code, each solve single-threaded inside, give the same verdict, why, notes and figures on every host but in a figure's last binary digits. Read on the Spark and on the Mac, a plate pulled off its bolts (the CAE suite's `through/pull.json`) gave its bolt's sheared area as 68.75557623214958 mm² on one and 68.7555762321496 on the other, its processor's rounding, while each host reads it the same every time. So the cases a candidate is compared by are read on one host, one whose budget holds its largest case: the first of them to take a slot sets it for the rest, and the budget line says so, and names any candidate whose cases moved, as a host failed them. Candidates spread across hosts. A host that fails a read takes no more jobs, and the read runs again on another, never read as the part's NO ANSWER. That covers a host that stops answering, Docker's own refusal or SSH's (exit 125, 126, 127 or 255, as for cores the host hasn't), and a reply of nothing at all. A read stopped at its limit on a remote host, which a slower host can reach where this one answers, is read again on another host too, and that host stays in use: so where a read ran never changes its verdict. Nor does a placement: where no host could take a case at all, the candidate reads "not read", and a read stopped before it began is cut off with the study. The same study read here alone and across hosts gives the same table (`tests/test_bench_remote.py`). The budget line says each host's budget, how many reads each ran and how long they took.

**The table as it fills in.** The study says the budget it used, and the most it ran at once, as it begins and at the top of `study.md`. `study.md` is written again as the loop next takes stock of what's landed: at each of the model's tool calls, and every second while it waits. A row still reading says so, and isn't counted as read or as failing; one the study's end cut off says it wasn't read. An ending, a limit or `stop`, waits for what's running and doesn't begin what's queued. An interrupt, or an error no tool answers for, stops what's running, Orca's slices and this study's containers, and writes the table so far.

**Each `load` is a bench job** (`bench.job`): its command, the files it reads in a folder of their own, and its limits, a unit any host with the same image could run, returning its reply and the files it saved into that folder. Here they run on this host (`run_here`); a runner for another host is ROADMAP M12's job runner (mqucifer/project-print), and nothing here assumes one host. The rounds harness's own bench calls are as they were.

## Queued by itself, from an approved design run

mqucifer/print-shop#359. The Sponsor, 2026-11-27: the study "is what print shop should be doing, learning from it", and of which: "Everything with a load case to start with the option to include flagged designs." So (`study.orders`):

- **On approval.** `scripts/rounds.py resume NAME --approve --by WHO [--study-limits FILE]` queues a study of each part the run delivers, where any of its needs is a `load` need: each approved file that's a part of the assembly its `load` needs read, in the assembly's order, with the run's own load cases (`--needs`), its folder for the part's fits (`--context`), and the side its bed need lays the part on, turned about its up axis by fit-bed's own turn (`--turn RX,RY,fit`). Queuing follows the approval and can't refuse or undo it: what goes wrong is said, and the run is approved as it was. As it's queued, what the study reads is copied into its order's inputs, `ROOT/RUN/studies/N-PART/inputs/`, each file with its hash: the approved file, and the assembly with every file it names, its parts' and each one's `with`s and band, the part's own the approved copy; one it names that isn't there refuses the study. Files are matched by the names the run gave them, as a file shared by several groups is renamed at review, and each is one part. An order isn't claimable until its inputs are copied; one stopped mid-copy is failed, and one left `copying` past 30 min, by a queuing killed outright, is failed wherever a queue, a retry or a worker looks, saying so. A part's file is matched by the path the run gave it, else by its name where only one part's file has it, and the copy is held to the approval's own hash. An order still open isn't queued again; one done for that approval is said; one failed is queued again as its next attempt, read and written in one transaction. Where no limits are given, it says so. `scripts/settings_study.py retry ORDER --root ROOT --by WHO` queues an order failed or done again as it was: its kind, cases, needs, limits and inputs, held to their hashes, as its next attempt.
- **A flagged design.** `scripts/settings_study.py queue RUN --by WHO [--file NAME]... [--case 'NAME=LOAD ARGS']... [--assembly FILE] [--limits FILE]` queues a study of each approved file of an approved run, or those named: with no load cases, for time, grams and finish only, or with the cases the Sponsor names, read on the assembly its `load` needs read, or the one named in its work folder. A part done or failed is queued again with these cases and limits, as its next attempt, and the worker is started for them.
- **One at a time, by themselves.** The approval that queues studies starts a worker for its root, detached, where none holds the root's lock (`ROOT/studies.lock`), and doesn't wait for it: it runs until nothing is queued, writing to `ROOT/studies.log`, and two started at once leave one. It runs from a stated checkout, `STUDY_CHECKOUT` in the Mac's settings, else this checkout's main one, with that checkout's own `.venv`, never a worktree, which a builder may remove mid-study, nor one whose code reads older orders than these, as its own script answers `settings_study.py orders-format`: that's said, "pull it". It's watched for 2 s, and an end at once is said, not that it started. A flagged order takes its part's material from the assembly whatever its cases. `scripts/settings_study.py work --root ROOT [--once]` is that worker, to start by hand too. Taking the root's lock, it fails any order still running, as its worker died with it; an interrupt fails its order before it's raised; and finding nothing queued, it lets the lock go and looks once more, so an order queued as it ended isn't stranded. It runs the queued studies of the design runs under `ROOT`, oldest first, one at a time, each reading in parallel within the host's budget as above. For each it holds what was copied to its hashes, and meshes the approved file in its own axes by the bench's image at Orca's own STEP defaults, as the refinement pass meshes one (`bench/refine.py`), a mesh past 600 s stopped by its container's name. The study is written beside them, `study.md` and all, and the order says where. `scripts/settings_study.py queued --root ROOT` lists each order and what came of it. No printer, arming or print queue is touched.
- **Its nozzle and filament** are the limits', else the Mac's settings: `STUDY_NOZZLE` in mm, and `STUDY_FILAMENTS`, a filament by the material the assembly gives the part, as `petg=Elegoo PETG; pla=Elegoo PLA; *=Elegoo PLA`, `*` for a part of none, as a flagged design with no assembly is, or one name for every part. An order with neither fails, saying so, before anything is meshed.

The orders are a table of the design runs' own ledger, `study_orders`, beside the approvals they follow.

## The Sponsor's limits

Given up front, kept with each queued study and binding on it (`study.limits`, `--limits FILE` to a study run by hand): one JSON object of `most_minutes`, `most_grams`, `patterns`, `wall_sequences`, `least_infill`, `most_infill`, `most_walls`, `nozzle` and `filament`; any other key is refused. The model is told them. A candidate past what's known before slicing, its pattern, wall order, infill or walls, the part's or a region's, is refused before it's sliced: as it would be sliced, what it asks over the profile's own, so a setting it leaves unset is held to the limits as the profile gives it. One Orca slices past the most time or grams is ruled out, isn't read further, and can't be recommended. The profile's own settings are read as the baseline whatever the limits, and can't be recommended past them. `study.md` says the limits, and under **Ruled out by the Sponsor's limits** each candidate they ruled out and why, sliced or not; a ruled-out candidate is never counted as failing.

**With no load cases**, a candidate passes on its slice and the limits, and the trade-off is time against grams; the table has no case columns, and `published` gives each pattern's lines and checked densities without the figures of a plastic `load` doesn't know.

## What the model can do

- **`published`**: what the published tests say of each pattern `load` reads (`bench/infill.py`, each cited there and in `docs/bench.md`): which way its lines run and whether they build walls through the layers, how stiff it is along its angle and across its layers at 20, 40 and 60%, what strain it takes, and from what density a test checks it; the walls' thickness by count, by Orca's bead spacing; and Orca 2.4.2's own words for each wall order. **Direction matters as much as density**: a pattern is strongest along its lines, walls run along the outline, and a pull across the layers is the layers' bond.
- **`read`**: a candidate (`study.candidate`), queued: it replies at once, so the model goes on while it's read, and asks for others it would read anyway. The part's `walls`, `top`, `bottom`, `infill`, `pattern` and `infill_angle` over the profile's own; its `wall_sequence`, for finish only, as `load` reads walls by their count in any order; its `turn`; and `regions`: a `box`, a `cylinder` or a band of `layers` as `bench/printed.py` takes them, or `{"joints": "all" or [names], "margin": MM, "faces": true, ...settings}` for a region round each of the part's joints: a cylinder round each bolt's hole, and round each fit and latch a box, or with `faces` a mesh of the part's own faces in it, `margin` deep (`candidate.faces_mesh`). Code bounds each: the infill 10 to 60% and the patterns `load` reads, walls 1 to 10 and shells 3 to 15. **A region with walls of its own is held to its depth** (mqucifer/print-shop#357): Orca prints it as an island, walled round its own outline from every side, so it holds one wall for each two bead spacings of its depth in the part, 0.81 mm with 0.45 mm lines at 0.2 mm, and one where it's narrower than that but a line's width or more. Read off Orca 2.4.2 on the bar of `tests/test_slice_regions.py`: a ring round its hole 1.0 to 1.4 mm deep laid 1 wall, 1.8 to 2.2 mm 2, 2.6 to 3.0 mm 3. Before slicing, the depth is read from the region's own section in the part (`regions.walls_held`): on each of up to 9 layers through it, for each point of its outline the largest circle in the section that reaches it, twice their median; and across the layers, their median. The reader counts a region's walls along its whole outline and takes the count most of it has, on most of its layers, so the depth is the section's typical width, not its fattest spot: a square tube 2.2 mm thick holds 2 walls whatever its corners, and a 1.2 mm arm with a 4 mm hook holds 1, as Orca builds them (mqucifer/print-shop#358's review). A face mesh 1 mm deep holds 1 wall. A deep face mesh's layers that lie in a face across the layers, at a part's top and bottom, hold the whole face: its median is its strip's where most of its layers are, and the reader's is too. A region asking more walls than it holds is refused before Orca runs, saying what fits and how deep it would need to be, as Orca would lay fewer and `load` would read them as asked; one that fits says its depth beside its reading. **Where it meets another region it's noted, not refused:** Orca 2.4.2 doesn't wall the border between two regions, so a ring under a later one keeps its whole depth for its walls, and the later one may hold more than its own section says; it's sliced, and the layers say. The line width and layer height are the profile's. Its reading comes by `wait`.
- **`wait`**: the readings that have landed since it last asked, in the candidates' order, waiting for one where none has, each as `read` used to give it: its time and grams, each case's worst figures, what Orca built in each region, and the trade-off so far. `recommend` is refused while any candidate is still reading.
- **`past_studies`**: the kept lessons from studies of parts with the same keys, and what those studies recommended.
- **`recommend`**: a candidate it read, or `none` where none passes, with its reason and what it found as lessons. Code refuses one that fails a case or has no answer under one, and any before it has read two candidates of its own: it's there to study the settings, not to restate them.

The profile's own settings are read first, by code, so every candidate is compared with them. Past a limit, or with the model out of reach, the study ends with the table so far and no recommendation, saying why.

## The figures, and what they rest on

Of each `load` reply the study reads the part's own figures (`study.reading.figures`): its skin pulled across its layers and stretched any way, against the material's limits; each core's, against its own; and each joint it's in, by its nearest figure to its limit. Each is a share of its limit, and its margin is what's left. **The case's own need is judged exactly as the design run's is,** by `rounds.needs`' own `number_at` and `_judge_number`: a list's index followed (`pairs.0.gap_mm`), a figure at its limit to arithmetic's noise passing, a limit of 0 and a figure of 0 or less judged as they are, and no figure at all failing. A candidate passes where every case is `OK` and every figure is within its limit. `NO ANSWER`, `UNREAD` and `DISAGREE` fail it, saying why.

**A region Orca didn't build as asked fails its candidate, as not as sliced.** `load` reads a region as asked, so where the reader of the layers (`slicer.regions`) finds Orca built less, as 2 walls where 5 were asked in a band too narrow for them, or the part's own where the region's were asked, `load` would read the part stronger than it prints. The candidate isn't read by `load`, the table says so, and it can't be recommended. What couldn't be read from the layers at all, such as a pattern Orca was given by name, is taken as asked, and the table says that too.

The table says what each figure rests on, from the limits of `load`'s as-printed reading (mqucifer/print-shop#337):
- **The infill model.** A core's figures are published tests of PLA, ABS and PETG, as shares of their own plastic's, none yet checked against a print from this printer: that's mqucifer/print-shop#340's coupons. Every figure of a printed part rests on them, the skin's too, as what the skin carries is what the core doesn't. **Below the density any published test of a pattern reaches** (`infill.checked_from`, mqucifer/print-shop#342's `unchecked`: 20% for grid and the line patterns, 40% for gyroid and triangles), no test checks a core at all: the table marks those figures `*`, the skin's beside them too, and the recommendation's own paragraph names each cell, by its pattern and density.
- **Joints re-solved solid.** What `load` solves again round a through-bolt's hole, a dovetail's neck and walls and its latch's tab reads the plastic solid, stronger than printed: read those figures with a margin.
- **One pass only.** A printed part `load` would read in two passes is `NO ANSWER`.

**The walls as built, a second reading** (mqucifer/print-shop#341's reader, from mqucifer/print-shop#342's review): `load` takes n walls as n of Orca's bead spacings, width − layer height × (1 − π/4), 0.814 mm for 2 walls at 0.45 and 0.2. The slice's layers say how wide the walls' band lies, the part's and each region's with walls of its own (`slicer.regions.band`): on the bar of `tests/test_slice_regions.py`, 0.901 mm for 2 walls and 1.697 for 4, a bead's width past its spacing. A gap of more than half a line's width past that says the settings alone don't give the skin `load` reads there.

## The ledger

A study isn't a print, so it has no row of `prints`. It's kept in tables of its own in the same file (`study.lessons`, created if missing): `settings_studies`, with the part, its features as it prints, its keys, the cases, every candidate and its figures, the recommendation and every tool call; and `study_lessons`, what it found, each a candidate keyed by the part's features: its traits (`setup.traits`, as print lessons are, mqucifer/print-shop#106) and its joints (`joint:through`, `joint:dovetail`, `joint:latch`, `joint:fit`, ...). The model's own findings are drawn with the candidates that show them as their evidence, and code draws one from the recommendation against the defaults. **A reviewer lets each through**, as print lessons are, and only then does it reach a later study of a part with every one of its keys:

```
uv run python scripts/settings_study.py lessons [STUDY]
uv run python scripts/settings_study.py accept ID --by "reviewer: WHO"
uv run python scripts/settings_study.py edit ID --by "reviewer: WHO" [--text T] [--keys K,K] --why W
uv run python scripts/settings_study.py reject ID --by "reviewer: WHO" --why W
```

## Tests

`tests/test_bench_remote.py` runs in CI too, its remote made up (`tests/fake_docker.py` in place of `docker -H ssh://HOST`, its volumes folders); `tests/test_bench_remote_docker.py` (`-m bench`) runs a job the remote's way over this host's own Docker; and `tests/test_bench_remote_live.py` (`-m remote`) reads a real `load` on a real remote host against the same one here, skipped unless `PRINT_SHOP_TEST_REMOTE`, `..._CORES` and `..._FLOOR` name it. `tests/test_settings_study.py` runs in CI: the bar of `tests/test_slice_regions.py`, a scripted model, a fake slicer and fake `load` replies, and a temporary ledger. `tests/test_settings_study_slicer.py` slices its candidates with the real Orca on the Mac (`-m slicer`). Every part in them is made up.
